W1 · LEARNING 01

从“需求描述”识别真正的审计问题

KZJ-M1-W1-L01

学习目标

能够把“帮我核一下”“找异常”“跑一下全年数据”等模糊要求转换成明确的审计问题。

核心内容

  • CAATs任务必须先有审计问题，例如验证接口完整性、识别未经授权交易、检查收入截止，而不是单纯“分析数据”。
  • 同一句业务要求可能对应不同审计目标，例如“订单和收入核一下”可能关注完整性、准确性或截止。
  • 审计问题应说明对象、期间、风险和期望回答的问题。
  • 分析结果最终需要支持控制测试、实质性程序、异常调查或其他明确审计目的。
  • 如果审计目标不清楚，后续数据范围、规则和异常标准都会发生偏差。
  • 开始编码前应能用1-2句话向Reviewer复述任务目的。

判断与执行步骤

  1. 复述原始任务要求。
  2. 提取需要验证的业务/审计风险。
  3. 明确期间和对象。
  4. 判断最终要支持哪类审计结论。
  5. 写成1-2句话的审计问题。
  6. 与任务提出人确认后再设计数据方案。

常用资料 / 审计证据

  • 项目任务说明。
  • 财审/IT审计程序。
  • 业务流程和控制矩阵。
  • 历史底稿仅作为背景参考。
  • 项目负责人确认记录。

应用场景

任务要求：“把全年订单和财务收入核一下，看有没有漏传或者异常。”编码前需要明确究竟关注接口完整性、收入完整性、金额一致性还是年末截止。

完成后应能回答

  • 这项任务最终要支持什么审计结论？
  • 如果审计目标从完整性变为截止，数据和规则会发生什么变化？
  • 什么时候必须先回去确认需求而不能直接写SQL？

W1 · LEARNING 02

业务口径与分析范围

KZJ-M1-W1-L02

学习目标

能够在取数和编码前明确订单、收入、退款、取消、发货等关键业务口径。

核心内容

  • 业务口径决定一条记录是否应进入总体，是CAATs最常见的差异来源之一。
  • 需要明确业务日期使用创建日、发货日、确认日还是会计记账日。
  • 订单状态需要区分已取消、关闭、部分发货、退款、补发、测试单等。
  • 金额口径需要明确含税/不含税、原币/本位币、折扣前/折扣后、正负方向。
  • 跨系统字段名称相同不代表业务含义完全一致。
  • 所有重要口径必须在代码之外形成文字说明，便于Review和后续复用。

判断与执行步骤

  1. 列出分析总体涉及的业务对象。
  2. 逐项定义关键状态。
  3. 定义期间口径。
  4. 定义金额和币种口径。
  5. 识别特殊交易和排除项。
  6. 把口径写入任务说明并确认。

常用资料 / 审计证据

  • 业务制度。
  • 系统字段说明。
  • 订单/交易状态字典。
  • 会计政策。
  • 客户访谈记录。

应用场景

小艾系统订单状态有“已发货、部分发货、已取消、退款完成”，金蝶收入按会计期间记录。若不先定义口径，年度订单与收入比较很容易产生大量假差异。

完成后应能回答

  • 为什么业务口径应该写在SQL之前？
  • 日期字段不同会怎样影响截止测试？
  • 哪些特殊交易应单独分析而不是直接排除？

W1 · LEARNING 03

数据需求与最小必要字段

KZJ-M1-W1-L03

学习目标

能够从审计问题反推数据表、字段、主键和关联关系，不先拿一堆数据再决定怎么分析。

核心内容

  • 数据需求必须服务审计问题，字段越多不代表分析越完整。
  • 至少需要识别业务主键、时间字段、状态字段、金额字段和关联键。
  • 跨系统核对前要确认是否存在一对一、一对多、多对一关系。
  • 主键可能是订单号、订单行号、业务单号+行号等组合键。
  • 字段缺失应在取数前暴露，否则编码到一半才发现无法验证。
  • 对敏感或大体量数据应遵循最小必要原则，减少无关字段和处理成本。

判断与执行步骤

  1. 从审计问题列出需要验证的事实。
  2. 为每个事实确定字段。
  3. 确定源系统和表。
  4. 确认主键/关联键。
  5. 确认期间和总体字段。
  6. 形成数据需求清单。
  7. 在编码前完成字段可用性检查。

常用资料 / 审计证据

  • 数据库表结构。
  • 数据字典。
  • 字段样例。
  • 接口Mapping。
  • 业务人员/IT访谈记录。

应用场景

要核对订单到收入是否完整，至少需要订单/订单行标识、发货状态/日期、收入凭证或业务单号、金额、币种和会计期间；仅有订单号和金额通常不够。

完成后应能回答

  • 什么字段属于“最小必要字段”？
  • 为什么订单号可能不是唯一主键？
  • 一对多关系不先确认会导致什么结果？

W1 · LEARNING 04

预期输出与异常定义

KZJ-M1-W1-L04

学习目标

能够在编码前明确最终交付是汇总、异常明细、核对结果还是可直接入底稿的证据表。

核心内容

  • 同一分析可以输出总体统计、差异明细、异常分层和核验结果等不同层次。
  • 预期输出要与使用者和审计程序匹配。
  • 异常必须在编码前有初步定义，例如源有目标无、金额差异超过阈值、状态不一致、跨期。
  • 输出应保留能够追溯到源数据的关键字段。
  • 需要明确哪些属于真正异常，哪些只是待核验记录。
  • 输出格式和字段要支持Reviewer复核，而不是只方便程序作者阅读。

判断与执行步骤

  1. 明确最终使用场景。
  2. 确定输出层级。
  3. 列出异常类型。
  4. 确定异常阈值或规则。
  5. 确定输出字段。
  6. 确定结果文件命名和存放。
  7. 与Reviewer确认验收标准。

常用资料 / 审计证据

  • 审计程序。
  • 历史交付样例。
  • 问题清单模板。
  • 底稿格式。
  • Reviewer反馈。

应用场景

“核收入差异”最终可能需要三个输出：总体核对汇总、未匹配明细、金额差异明细。仅输出一张SQL结果表往往不足以支持底稿。

完成后应能回答

  • 谁会使用这个输出？
  • 异常和待核验记录有什么区别？
  • 哪些字段必须保留以便回溯源数据？

W1 · LEARNING 05

限制条件、假设与不可验证事项

KZJ-M1-W1-L05

学习目标

能够在任务开始时识别数据、系统、期间和业务规则限制，避免把假设写成事实。

核心内容

  • 常见限制包括数据缺失、字段口径不明、历史数据迁移、时区差异、接口留存不足。
  • 假设可以暂时用于推进，但必须明确标记并后续验证。
  • 无法验证的事项应说明对分析结论的影响。
  • 历史底稿中的口径不能自动沿用到新客户或新期间。
  • 技术可实现不等于审计上可接受，例如无法验证总体完整的数据分析不能直接支持完整性结论。
  • 限制条件应进入底稿或运行说明，而不是只存在个人记忆中。

判断与执行步骤

  1. 列出当前已知限制。
  2. 标记使用的假设。
  3. 判断哪些假设必须确认。
  4. 评估限制对结论的影响。
  5. 确定替代数据或程序。
  6. 在任务说明和底稿留痕。

常用资料 / 审计证据

  • 数据缺口说明。
  • 系统迁移说明。
  • 字段定义。
  • 历史底稿。
  • 项目沟通记录。

应用场景

客户只能提供2025年3月以后接口日志，但审计期间为全年。程序仍可分析3-12月，但不能据此直接对全年接口运行作完整结论。

完成后应能回答

  • 什么属于可接受假设，什么必须先验证？
  • 限制条件如何影响结论措辞？
  • 技术结果正确但总体不完整时能支持什么结论？

W1 · LEARNING 06

需求确认与替代方案

KZJ-M1-W1-L06

学习目标

能够在发现需求不明确或原方案不够优时，先确认硬性目标，再提出可比较的替代方案。

核心内容

  • 需求确认应集中在会影响结论、范围或交付形式的关键问题。
  • 不要把所有细节都变成反复询问；可自行判断的技术实现应自己推进。
  • 当原要求并非最优时，应先确认必须满足的审计目标、时间和交付要求。
  • 替代方案应说明优点、限制、额外成本和对结论的影响。
  • 项目负责人最终决定后，按照确认版本执行并保留决策记录。
  • 避免未经确认直接改变审计方法，即使技术方案看起来更好。

判断与执行步骤

  1. 识别不确定点。
  2. 区分必须确认与可自行判断事项。
  3. 形成初步方案。
  4. 准备替代方案。
  5. 说明两种方案差异。
  6. 向负责人确认。
  7. 记录最终范围并执行。

常用资料 / 审计证据

  • 任务拆解卡。
  • 项目沟通记录。
  • 邮件/即时通讯确认。
  • 方案比较。
  • Review记录。

应用场景

项目原要求用订单号直接匹配收入，但实际存在一单多行和拆单发货。可以提出按订单行+发货批次匹配，但应先说明为什么原方法会产生误差并确认交付口径。

完成后应能回答

  • 哪些问题需要在编码前确认？
  • 什么时候可以直接自行优化，什么时候必须确认？
  • 提出替代方案时最少要说明哪些内容？

W2 · LEARNING 01

项目结构、文件命名与代码分层

KZJ-M1-W2-L01

学习目标

能够让CAATs项目的输入、代码、中间结果、输出和说明文件具有统一、清晰、可识别的结构。

核心内容

  • 项目目录应区分原始输入、处理代码、中间数据、最终输出、日志和文档。
  • 文件命名应包含项目/程序用途、期间、版本或运行日期等必要信息。
  • 代码应按读取、清洗、规则、核验、输出等模块组织。
  • SQL长脚本应使用清晰CTE、临时表或分阶段表，不把所有逻辑挤在一个语句中。
  • 中间结果是否保留取决于可复核需要和数据敏感性。
  • 目录和命名的目标是让非作者能够快速找到数据来源、执行入口和最终结果。

判断与执行步骤

  1. 整理现有项目目录。
  2. 识别输入/代码/输出混放问题。
  3. 制定命名规则。
  4. 按处理阶段拆分代码。
  5. 明确最终执行入口。
  6. 补README说明目录结构。

常用资料 / 审计证据

  • 旧CAATs目录。
  • 团队共享目录规范。
  • 脚本文件。
  • 历史输出。
  • README模板。

应用场景

一个项目目录里同时存在final.xlsx、final2.xlsx、最新.sql、最新改.sql、结果0821.xlsx。重构后需要让其他同事能够明确识别当前版本和运行顺序。

完成后应能回答

  • 一个标准CAATs目录至少应分哪些层？
  • 文件名需要包含哪些信息？
  • 什么时候应保留中间结果？

W2 · LEARNING 02

参数化与期间处理

KZJ-M1-W2-L02

学习目标

能够把期间、阈值、路径、组织和其他常变条件从核心逻辑中分离，减少硬编码。

核心内容

  • 审计期间、公司编码、币种、阈值、文件路径等不应散落在代码各处。
  • 参数应集中配置，并给出默认值、格式和允许范围。
  • 日期边界要明确包含/不包含关系，避免月末和年末漏数。
  • 多主体、多期间运行应避免复制多份脚本。
  • 参数修改应被运行记录保存，确保结果可复现。
  • 阈值属于审计规则时，还要记录业务/审计依据，而不仅是技术配置。

判断与执行步骤

  1. 找出所有硬编码参数。
  2. 分类业务参数和技术参数。
  3. 集中到配置区。
  4. 定义格式校验。
  5. 测试期间边界。
  6. 将实际运行参数写入日志。

常用资料 / 审计证据

  • 旧脚本。
  • 项目期间。
  • 审计规则说明。
  • 配置文件。
  • 运行日志。

应用场景

程序筛选12月异常时写死`date >= '2025-12-01' and date <= '2025-12-31'`。参数化后需考虑时间戳、跨时区以及下一年度复用。

完成后应能回答

  • 哪些内容最应该参数化？
  • 阈值参数为什么需要审计依据？
  • 运行日志为什么要保存实际参数？

W2 · LEARNING 03

输入数据校验

KZJ-M1-W2-L03

学习目标

能够在程序正式执行前检查输入文件、字段、类型、期间、记录数和关键值是否符合预期。

核心内容

本周不再关注代码是否“漂亮”，而是把整套CAATs放回审计底稿：为什么做、规则依据是什么、异常是否真实、证据支持到哪里、最终怎样写结论。

本周成果：输出1套标准CAATs交付包：任务说明 + 数据说明 + 代码 + 运行记录 + 异常核验 + 审计底稿。

W4 · LEARNING 01

从审计风险到数据规则

KZJ-M1-W4-L01

学习目标

能够让每条分析规则对应明确的审计风险、控制目标或财报认定。

核心内容

  • 规则不是因为“能查”就应该执行，必须说明其审计目的。
  • 权限规则可能对应未授权访问；接口规则可能对应完整性/准确性；交易规则可能对应发生、截止等认定。
  • 规则阈值需要有制度、业务或审计依据。
  • 规则应说明适用总体、条件和例外。
  • 一个审计问题可有多条规则，多条规则也可能服务同一结论。
  • 规则说明需要Reviewer不看代码也能理解。

判断与执行步骤

  1. 明确审计问题。
  2. 写风险/认定。
  3. 定义总体。
  4. 写规则逻辑。
  5. 说明阈值依据。
  6. 说明预期异常。
  7. 与程序和底稿交叉引用。

常用资料 / 审计证据

  • 审计程序。
  • 控制制度。
  • 业务规则。
  • 财审认定。
  • 规则说明。

应用场景

规则“离职日期后仍有系统登录”应明确用于验证离职后未授权访问风险；不能只因为能够关联HR和日志就做这个分析。

完成后应能回答

  • 每条规则最少要说明什么审计依据？
  • 阈值怎么避免变成拍脑袋？
  • 规则和审计结论有什么关系？

W4 · LEARNING 02

异常与误报的分层

KZJ-M1-W4-L02

学习目标

能够把规则命中结果分为高风险异常、待核验、正常业务原因或数据问题。

核心内容

  • 规则命中不等于审计问题。
  • 需要识别误报来源，例如业务时间差、系统状态定义、重复数据、合理例外。
  • 可按金额、权限、频率、期间、实际操作等维度分层。
  • 高风险异常优先详细核验，中低风险可以抽样。
  • 规则本身误报率过高时，应反过来优化规则。
  • 分层过程应保留原始命中总体和每类处理结果。

判断与执行步骤

  1. 保留完整命中总体。
  2. 选择风险分层字段。
  3. 建立高/中/低分类。
  4. 抽取高风险核验。
  5. 抽样中低风险。
  6. 记录误报原因。
  7. 必要时迭代规则。

常用资料 / 审计证据

  • 异常总体。
  • 权限/金额字段。
  • 业务说明。
  • 核验样本。
  • 规则版本记录。

应用场景

筛出500个离职后Active账号，其中450个是从未启用的历史账号，30个无登录，20个有离职后登录。真正需要深入核验的重点应进一步集中。

完成后应能回答

  • 为什么异常数量不能直接等于问题数量？
  • 误报率高说明什么？
  • 规则优化后如何保留前后版本？

W4 · LEARNING 03

异常核验与审计证据链

KZJ-M1-W4-L03

学习目标

能够从CAATs命中记录继续取得业务、系统和财务证据，形成完整证据链。

核心内容

  • CAATs通常用于识别异常，不自动完成异常定性。
  • 核验需要回答谁、何时、做了什么、业务结果和财务结果。
  • 权限异常可结合HR、角色、登录和操作日志。
  • 接口异常可结合源系统、接口日志、目标系统和会计记录。
  • 交易异常可结合业务单据、审批、凭证、银行或第三方证据。
  • 证据链应支持Reviewer从异常结果追到最终判断。

判断与执行步骤

  1. 选取需核验异常。
  2. 写异常事实。
  3. 列所需补充证据。
  4. 关联业务/系统数据。
  5. 追踪财务结果。
  6. 识别仍有缺口。
  7. 形成初步定性。

常用资料 / 审计证据

  • 异常明细。
  • 系统日志。
  • 业务单据。
  • 财务凭证。
  • 第三方证据。

应用场景

程序发现12月31日5笔订单已发货但ERP无收入。还要检查发货是否真实、是否1月补记、金额以及财审截止影响。

完成后应能回答

  • CAATs结果支持到哪一步？
  • 什么情况下必须补业务证据？
  • 异常如何继续追到财务科目和认定？

W4 · LEARNING 04

结论边界与停止条件

KZJ-M1-W4-L04

学习目标

能够在证据足够时形成结论并停止继续分析，避免无边界扩展数据和规则。

核心内容

  • 结论强度必须与数据总体和核验证据匹配。
  • 无法证明全年总体时，不能写全年完整性无异常。
  • 识别异常但未验证实际影响时，应写待核验或控制风险，不直接写财务错报。
  • 停止条件应在分析前定义，例如高风险异常全部核验+中风险抽样达到预期。
  • 继续增加字段或规则如果不会改变结论，应考虑停止。
  • 未解决限制和残余风险必须明确披露。

判断与执行步骤

  1. 回顾审计问题。
  2. 检查总体可靠性。
  3. 检查异常核验覆盖。
  4. 判断是否达到停止条件。
  5. 形成结论。
  6. 列限制和未决事项。
  7. 停止无增量价值分析。

常用资料 / 审计证据

  • 总体校验。
  • 异常核验结果。
  • 审计程序。
  • 限制说明。
  • Reviewer意见。

应用场景

接口分析5笔差异均已确认次日补传且不影响年末会计期间。继续增加十几个日志字段不会改变结论，应停止并形成底稿。

完成后应能回答

  • 什么时候可以停止分析？
  • 什么情况下结论需要缩小范围？
  • 如何表达“有异常但未影响审计结论”？

W4 · LEARNING 05

CAATs与审计底稿衔接

KZJ-M1-W4-L05

学习目标

能够把程序目的、数据、规则、校验、异常和结论完整写入可复核底稿。

核心内容

  • 底稿应先写审计目标和程序目的，不从代码截图开始。
  • 数据部分记录来源、总体完整性和关键字段。
  • 规则部分用业务语言说明，不要求Reviewer阅读代码才能理解。
  • 程序执行应引用代码版本和运行日志。
  • 结果部分包括总体、命中异常、核验和最终剩余异常。
  • 结论部分说明对控制、科目/认定或财审程序的影响。

判断与执行步骤

  1. 写审计目标。
  2. 写数据来源和可靠性。
  3. 写分析规则。
  4. 引用程序/版本。
  5. 汇总结果。
  6. 记录异常核验。
  7. 形成结论和限制。

常用资料 / 审计证据

  • 标准工作底稿。
  • 代码版本。
  • 运行日志。
  • 异常清单。
  • 核验证据。

应用场景

工作底稿不能只写“执行SQL见附件，识别153笔异常”。需要让Reviewer知道153笔怎么来的、是否核验、剩余问题是什么。

完成后应能回答

  • 一份CAATs底稿最少要包含哪些内容？
  • 哪些技术信息放README，哪些必须进入底稿？
  • Reviewer不看代码能否理解审计逻辑？

W4 · LEARNING 06

标准CAATs交付包与交接

KZJ-M1-W4-L06

学习目标

能够形成可直接归档、Review、交接和后续项目复用的完整交付包。

核心内容

  • 标准包至少包括任务说明、数据需求/字典、代码、参数、README、运行日志、结果和审计底稿。
  • 原始输入与客户敏感数据按项目要求存储，不与代码随意打包复制。
  • 需要标记最终审计版本和归档版本。
  • 复用时先重新确认业务口径和审计目的，不直接复制规则。
  • 交接需要说明已知限制、依赖环境和未解决事项。
  • 月末标准包将作为后续CAATs规范模板的第一版。

判断与执行步骤

  1. 整理最终目录。
  2. 删除无效临时文件。
  3. 标记最终版本。
  4. 核对底稿引用。
  5. 补交接说明。
  6. 让Reviewer按清单验收。
  7. 归档标准模板。

常用资料 / 审计证据

  • 任务说明。
  • 数据字典。
  • 代码/配置。
  • README。
  • 运行日志。
  • 结果/底稿。

应用场景

项目结束后，另一名同事应能从标准包快速判断分析目的、重新运行程序、复核异常来源并理解最终结论，而不需要原作者口头讲解。

完成后应能回答

  • 标准交付包最少有哪些文件？
  • 哪些内容可以复用，哪些必须在新项目重新确认？
  • 怎样判断一个CAATs程序真正达到“可交接”？

月末综合验收｜订单与收入CAATs案例

场景：项目要求核对全年电商订单与ERP收入，识别漏传、重复、金额异常和年末截止问题。订单来自OMS，发货来自WMS，收入来自ERP，退款来自平台数据。

  1. 先写任务说明：审计问题、业务口径、期间、输入、输出和限制。
  2. 列出最小必要数据表、字段、主键和关联关系。
  3. 设计输入和输出校验。
  4. 设计至少3类异常规则并说明审计依据。
  5. 说明如何验证总体完整性和字段可靠性。
  6. 选1类异常设计后续核验证据链。
  7. 说明最终底稿结论和停止条件。

NEXT MONTH

第2个月计划生成依据

第2个月不再单纯增加代码难度，而是根据本月实际结果决定往哪一层升级。

工程规范稳定

如果任务拆解和可复现已稳定，第2个月减少规范训练，直接要求新项目全部采用标准包。

审计判断仍弱

如果规则、异常核验和结论仍依赖Reviewer，第2个月增加Scope、证据判断和财审连接训练。

能力升级

达到本月目标后，可进入权限/SoD、日志行为、接口一致性、会计分录等更复杂CAATs场景，并开始沉淀可复用框架。
