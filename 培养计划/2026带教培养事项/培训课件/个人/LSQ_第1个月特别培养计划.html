W1 · LEARNING 01

应用系统、数据库与操作系统

LSQ-M1-W1-L01

学习目标

能够理解App、DB、OS三层关系，并判断不同技术资料属于哪一层。

核心内容

  • 应用系统是业务人员直接使用的界面和功能，例如ERP、OA、WMS。
  • 数据库保存业务数据、配置、用户和交易记录，常见有Oracle、SQL Server、MySQL等。
  • 操作系统承载应用和数据库进程，例如Windows Server、Linux。
  • 应用账号、数据库账号、操作系统账号属于不同权限层级。
  • 数据库直接修改可能绕过应用控制，因此DB高权限通常需要单独关注。
  • 理解三层的目的，是为了知道权限、日志、变更、备份分别应去哪一层取证。

判断与执行步骤

  1. 确认应用名称和业务用途。
  2. 确认数据库类型和部署方式。
  3. 确认操作系统。
  4. 识别各层管理员。
  5. 确认各层日志位置。
  6. 把每份客户资料归到App/DB/OS。

常用资料 / 审计证据

  • 系统架构图
  • 管理员清单
  • 应用配置
  • 数据库账户/审计日志
  • 操作系统账户/安全日志

应用场景

ERP运行在Windows Server上，后台数据库为SQL Server。应用管理员只能配置ERP功能，DBA可直接查询数据库。需要分别识别两类权限和日志。

完成后应能回答

  • 应用管理员和DBA分别能做什么？
  • 为什么数据库权限可能绕过应用控制？
  • 一张Windows截图能不能证明ERP应用权限？

W1 · LEARNING 02

账号认证与身份管理

LSQ-M1-W1-L02

学习目标

能够理解账号从建立、认证到授权的基本链路，并识别本地账号、AD/域账号和SSO差异。

核心内容

  • 身份认证回答“你是谁”，授权回答“你能做什么”。
  • 系统可能使用本地账号、Windows AD、LDAP、SSO或MFA。
  • 本地账号由应用自身管理，域账号由集中身份平台管理。
  • SSO并不代表所有权限统一管理，应用内角色可能仍需单独维护。
  • MFA增强认证强度，但不能替代离职停用和权限审批。
  • 审计需要明确认证源、账号生命周期和应用角色分别在哪管理。

判断与执行步骤

  1. 确认登录方式。
  2. 确认认证源。
  3. 确认账号新增/停用触发机制。
  4. 确认应用角色维护位置。
  5. 确认MFA和密码策略。
  6. 识别共享/服务账号。

常用资料 / 审计证据

  • 登录页面
  • AD/SSO配置
  • 应用账号清单
  • 角色清单
  • MFA配置
  • 用户生命周期流程

应用场景

客户ERP通过AD单点登录，但ERP角色仍由ERP管理员单独配置。离职时AD停用可阻止登录，但角色配置仍需理解。

完成后应能回答

  • 认证与授权有什么区别？
  • SSO为什么不等于权限管理完成？
  • MFA可以解决哪些风险，不能解决哪些？

W1 · LEARNING 03

系统接口与数据流

LSQ-M1-W1-L03

学习目标

能够理解源系统、接口程序、目标系统和字段映射的基本关系。

核心内容

  • 接口用于在系统之间自动传递数据。
  • 接口可能实时、定时批处理或文件方式运行。
  • 源系统产生原始业务数据，目标系统接收并进一步处理。
  • Mapping定义源字段如何对应目标字段。
  • 接口失败可能造成漏传、重复、跨期或字段转换错误。
  • 审计需要同时关注源数据、接口执行和目标落地。

判断与执行步骤

  1. 识别源系统和目标系统。
  2. 确认传输频率。
  3. 确认关键字段。
  4. 确认Mapping。
  5. 确认失败/重跑机制。
  6. 确认最终落地位置。

常用资料 / 审计证据

  • 接口清单
  • Mapping文档
  • 接口日志
  • 失败队列
  • 源/目标明细

应用场景

WMS每日将出库数据传ERP，ERP据此结转营业成本。需要知道接口什么时候跑、失败在哪里看、重跑后怎样证明最终落地。

完成后应能回答

  • Interface与应用系统有什么区别？
  • 为什么只看“接口成功”还不够？
  • 源系统和目标系统各自能证明什么？

W1 · LEARNING 04

日志是什么、分别记录什么

LSQ-M1-W1-L04

学习目标

能够区分登录日志、操作日志、数据库审计日志、系统日志和接口日志。

核心内容

  • 登录日志记录谁在什么时候登录或退出。
  • 操作日志记录用户在应用内执行的关键业务或配置动作。
  • 数据库审计日志记录数据库层登录、DDL/DML等活动，取决于配置。
  • 操作系统安全日志记录OS登录、服务和系统事件。
  • 接口/作业日志记录批次执行、成功失败和错误信息。
  • 不同日志证明不同事实，不能用一张日志截图代替全部层级。

判断与执行步骤

  1. 先明确要证明什么。
  2. 确定该事件发生在哪一层。
  3. 找对应日志。
  4. 确认日志字段和时间。
  5. 确认日志保留期。
  6. 判断是否需要其他日志交叉验证。

常用资料 / 审计证据

  • 应用审计日志
  • 数据库审计日志
  • Windows/Linux安全日志
  • 接口日志
  • 作业日志

应用场景

要确认离职用户是否在离职后进入ERP，应用登录日志可能最直接；要确认DBA是否直接修改数据库，则需要数据库审计日志。

完成后应能回答

  • “系统有日志”为什么不够？
  • 操作日志和登录日志有什么差别？
  • 审计问题如何决定应该取哪类日志？

W1 · LEARNING 05

批处理、调度与后台作业

LSQ-M1-W1-L05

学习目标

能够理解定时任务如何自动执行接口、月结、备份和报表，并知道失败证据在哪里。

核心内容

  • 批处理是系统在后台一次处理一批数据或任务。
  • 调度器负责按时间、依赖关系触发作业。
  • 常见作业包括接口同步、财务月结、报表生成、批量计算、备份。
  • 作业需要有状态、开始/结束时间、错误信息和失败处理。
  • 失败后的自动重试、人工重跑可能影响期间和数据完整性。
  • 关键财务作业应关注是否有人监控。

判断与执行步骤

  1. 取得关键作业清单。
  2. 确认调度频率。
  3. 识别财务相关作业。
  4. 查看执行日志。
  5. 检查失败/重跑。
  6. 追最终业务和财务结果。

常用资料 / 审计证据

  • 作业调度截图
  • 作业日志
  • 失败告警
  • 重跑记录
  • 月结/接口结果

应用场景

每天23:00执行WMS→ERP接口，12月31日失败、1月1日重跑。需要评估数据是否跨期。

完成后应能回答

  • 批处理和Interface是什么关系？
  • 作业“重跑成功”还需要验证什么？
  • 哪些后台作业可能影响财务报表？

W1 · LEARNING 06

备份对象与备份链路

LSQ-M1-W1-L06

学习目标

能够理解应用文件、数据库、操作系统和虚拟机备份的差异。

核心内容

  • 备份对象可能是数据库、应用文件、文件服务器、虚拟机或整机。
  • 财务数据通常重点关注数据库，但恢复系统还可能依赖应用文件和配置。
  • 全备、增量、日志备份具有不同恢复用途。
  • 备份软件首页只能说明工具存在或当前状态，不证明策略、全年执行和可恢复。
  • 备份频率和保留应结合RPO、业务重要性和数据可重建性。
  • 备份应最终回答：发生故障后能否恢复到可接受状态。

判断与执行步骤

  1. 确认关键数据在哪里。
  2. 确认备份对象。
  3. 了解备份类型和频率。
  4. 确认保留周期。
  5. 查看执行状态。
  6. 了解恢复方法。

常用资料 / 审计证据

  • 备份策略
  • 备份任务配置
  • 执行日志
  • 介质/存储说明
  • 恢复测试记录

应用场景

客户说ERP每天备份，但只给备份软件首页。需要继续确认具体备份的是ERP数据库、服务器还是文件，以及任务执行和恢复情况。

完成后应能回答

  • App、DB、OS是否都必须分别备份？
  • 一张备份首页截图能证明什么？
  • 备份频率怎样和业务要求连接？

W2 · LEARNING 01

备份策略与备份任务

LSQ-M1-W2-L01

学习目标

能够区分制度层的备份策略和系统层的具体备份任务配置。

核心内容

  • 备份策略说明企业要求：备什么、多久备一次、保留多久、保存在哪里。
  • 备份任务配置说明某个数据库/服务器实际如何执行策略。
  • 需要关注任务对象、计划时间、类型、保留和目标存储。
  • 制度要求与配置不一致时，要确认实际执行和风险。
  • 备份策略不能脱离系统重要性和恢复目标单独评价。
  • 关键系统范围遗漏本身可能构成设计问题。

判断与执行步骤

  1. 获取备份制度。
  2. 列关键系统/数据库。
  3. 逐一对应备份任务。
  4. 核对频率/保留。
  5. 确认存储位置。
  6. 识别策略与配置差异。

常用资料 / 审计证据

  • 备份制度
  • 备份任务配置
  • 系统清单
  • 数据库清单
  • RTO/RPO

应用场景

制度要求核心数据库每日备份，但发现一个新上线ERP数据库未纳入备份任务。需要判断是否为范围遗漏。

完成后应能回答

  • 策略与任务有什么区别？
  • 怎样证明关键数据库都纳入备份？
  • 保留周期应该依据什么判断？

W2 · LEARNING 02

备份执行日志与失败处理

LSQ-M1-W2-L02

学习目标

能够从全年执行记录判断备份任务是否持续运行，并识别失败后的处理。

核心内容

  • 当前成功截图只能证明当前或某一天状态。
  • 全年执行有效性通常需要看期间日志或任务历史。
  • 失败记录要关注发生日期、原因、告警、重跑和最终成功状态。
  • 连续失败比偶发失败风险更高。
  • 失败后无告警、无人处理可能说明监控控制不足。
  • 最终要判断期间内是否存在未被覆盖的恢复窗口。

判断与执行步骤

  1. 获取期间任务历史。
  2. 筛选失败/警告。
  3. 抽取失败样本。
  4. 看告警。
  5. 看重跑/补备。
  6. 判断是否形成未覆盖期间。

常用资料 / 审计证据

  • 任务历史
  • 失败日志
  • 告警邮件
  • 事件工单
  • 重跑记录

应用场景

全年备份历史有12次失败，其中11次当日重跑成功，1次直到3天后恢复。需要重点评价这3天窗口。

完成后应能回答

  • 为什么不能只抽成功日志？
  • 失败后重跑成功证明到哪一步？
  • 如何评价长期未处理失败？

W2 · LEARNING 03

恢复测试与恢复能力

LSQ-M1-W2-L03

学习目标

能够理解备份成功和可恢复的区别，并设计恢复测试取证。

核心内容

  • 备份文件存在不代表文件未损坏或可以恢复。
  • 恢复测试验证备份介质、恢复步骤和数据是否可用。
  • 测试应明确恢复对象、恢复时间和结果。
  • 实际故障恢复、服务器迁移或灾备切换有时可作为替代证据。
  • 恢复测试频率要结合系统重要性和风险。
  • 恢复证据应证明恢复结果，而不只是“点击了恢复按钮”。

判断与执行步骤

  1. 确认是否有恢复测试要求。
  2. 获取最近恢复测试。
  3. 确认测试对象。
  4. 确认恢复过程。
  5. 确认恢复结果验证。
  6. 无正式测试时找实际恢复证据。

常用资料 / 审计证据

  • 恢复测试报告
  • 恢复日志
  • 恢复后验证截图
  • 迁移工单
  • 灾备演练

应用场景

客户没有年度恢复演练，但半年前服务器迁移时从备份恢复数据库并完成业务验证。可以评估该记录是否提供部分恢复能力证据。

完成后应能回答

  • 备份成功与恢复成功的差别是什么？
  • 恢复测试最重要的结果证据是什么？
  • 什么可以作为替代恢复证据？

W2 · LEARNING 04

批处理作业清单与关键作业

LSQ-M1-W2-L04

学习目标

能够识别哪些后台作业与财务数据相关，而不是要求客户把所有任务都拿来。

核心内容

  • 制度/流程说明证明设计要求，不证明实际执行。
  • 访谈是理解来源，需要其他证据支撑关键执行结论。

判断与执行步骤

  1. 先写待证明事项。
  2. 判断所需证据类型。
  3. 评价现有资料。
  4. 判断时点/期间覆盖。
  5. 判断来源和完整性。
  6. 识别补充证据。

常用资料 / 审计证据

  • 截图
  • 配置导出
  • 日志
  • 系统报表
  • 制度
  • 访谈纪要

应用场景

客户用当前用户列表截图证明“全年离职账号均及时停用”。该截图只能证明当前状态，不能证明全年及时性。

完成后应能回答

  • 截图最常见的局限是什么？
  • 什么时候必须取得期间日志/历史记录？
  • 制度和执行证据为什么不能混用？

W4 · LEARNING 03

PBC如何从控制目标反推

LSQ-M1-W4-L03

学习目标

能够写出具体、可执行且与审计目标对应的资料需求。

核心内容

  • PBC应说明系统、期间、范围和需要字段。
  • 不要只写“提供备份资料”“提供日志”。
  • 总体资料和样本资料应区分。
  • 资料用途要清楚，便于客户理解为什么需要。
  • 如果理想证据不存在，应设计替代资料。
  • PBC过度宽泛会增加客户沟通成本和无效资料。

判断与执行步骤

  1. 写控制目标。
  2. 列需要证明的事实。
  3. 逐项对应证据。
  4. 写清系统/期间/字段。
  5. 区分总体与样本。
  6. 准备替代证据。
  7. 确定优先级。

常用资料 / 审计证据

  • PBC清单
  • 控制目标卡
  • 系统清单
  • 证据模板
  • 客户沟通记录

应用场景

要测试数据库高权限，不应只写“请提供数据库权限截图”，而应明确数据库用户总体、角色/权限、高权授权、期间登录/操作日志等。

完成后应能回答

  • 一个好的PBC最少包含哪些信息？
  • 为什么PBC要写用途？
  • 什么时候应提前准备替代资料需求？

W4 · LEARNING 04

资料不一致时如何判断

LSQ-M1-W4-L04

学习目标

能够在客户说明、系统截图、清单和日志互相不一致时定位真实事实。

核心内容

  • 客户说明与系统实际配置冲突时，应以可验证证据为基础。
  • 名单类资料可能是人工整理，需要追溯系统来源。
  • 当前配置与历史日志不一致可能说明期间发生变更。
  • 多个系统时间戳可能因时区不同导致表面差异。
  • 差异应先确定口径和数据来源，再判断控制问题。
  • 不要为了“对上”而忽略无法解释差异。

判断与执行步骤

  1. 列出冲突的两类事实。
  2. 确认各资料来源。
  3. 确认期间/时区/口径。
  4. 寻找更直接证据。
  5. 解释差异。
  6. 保留未解决事项。

常用资料 / 审计证据

  • 系统原始记录
  • 客户清单
  • 日志
  • 配置变更历史
  • 访谈

应用场景

客户权限表显示某用户3月1日停用，但系统日志显示3月5日仍登录。需要确认清单是否为人工维护、账号是否同名、时间口径等。

完成后应能回答

  • 资料冲突时应优先相信什么？
  • 人工整理清单有什么风险？
  • 怎样避免为了消除差异直接接受解释？

W4 · LEARNING 05

证据不足与结论边界

LSQ-M1-W4-L05

学习目标

能够准确表达现有证据支持的范围，避免因为看不懂或资料不足而过度定性。

核心内容

  • 资料不足不是自动等于控制缺陷。
  • 证据只能证明当前配置时，不能写全年持续有效。
  • 只证明有控制设计时，不能写执行有效。
  • 无法取得关键历史证据时，应说明限制和替代程序。
  • 结论可以是“目前无法支持依赖”而不是武断写“控制失效”。
  • 结论边界本身应进入底稿。

判断与执行步骤

  1. 明确测试目标。
  2. 列现有证据。
  3. 逐项写能证明什么。
  4. 识别期间/总体缺口。
  5. 设计替代程序。
  6. 形成当前结论。
  7. 保留限制。

常用资料 / 审计证据

  • 证据清单
  • 替代资料
  • 限制说明
  • Review记录
  • 底稿结论

应用场景

客户只提供当前密码策略截图，但无法提供全年变更记录。可以评价当前配置，但全年持续有效性需要其他证据。

完成后应能回答

  • “资料不足”和“控制缺陷”有什么区别？
  • 怎样写一个有边界的结论？
  • 什么时候只能写“无法依赖”而不能写“失效”？

W4 · LEARNING 06

陌生系统综合取证

LSQ-M1-W4-L06

学习目标

能够面对陌生产品时，不依赖具体界面记忆，而是从技术对象和控制目标设计取证。

核心内容

  • 不认识产品名称时先确认它的用途和技术层级。
  • 界面位置可能不同，但控制目标不会因为产品不同而改变。
  • 先问“要证明什么”，再找“哪里能看到”。
  • 可以让客户演示、查产品文档或由IT解释，但关键事实仍需留证据。
  • 陌生系统最容易出现把错误层级截图当作目标证据。
  • 综合取证应保留系统名称、功能、版本、资料位置和判断。

判断与执行步骤

  1. 确认系统用途。
  2. 画最小技术关系。
  3. 确定控制目标。
  4. 设计PBC。
  5. 现场看资料。
  6. 判断证据。
  7. 补取缺口。
  8. 形成结论。

常用资料 / 审计证据

  • 系统介绍
  • 架构图
  • 现场演示
  • 产品配置
  • 日志/导出
  • PBC记录

应用场景

遇到一套从未见过的云ERP，不需要先熟悉所有菜单。先确认认证、用户权限、变更方式、日志、备份责任和关键接口，再围绕审计目标取证。

完成后应能回答

  • 陌生产品时第一步是什么？
  • 哪些信息与产品无关、每个系统都要问？
  • 如何避免依赖AI猜界面和字段？
