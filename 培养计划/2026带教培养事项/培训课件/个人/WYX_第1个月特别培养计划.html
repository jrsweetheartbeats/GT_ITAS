W1 · LEARNING 01

把审计目标改写成要回答的问题

WYX-M1-W1-L01

学习目标

能够把一句抽象目标转成若干具体、可验证的问题。

核心内容

  • “验证离职账号及时停用”至少要回答：谁离职、账号何时停用、时限要求是什么、期间是否仍能登录。
  • “验证IPE可靠”至少要回答：报表来自哪里、查询参数是什么、总体是否完整、关键字段是否准确。
  • 目标拆解要围绕最终审计结论，不是围绕历史底稿行数。
  • 每个子问题应能对应一种证据。
  • 目标不明确时，应先确定会影响程序的关键定义。
  • 程序草案形成后应能向Reviewer说明每一步与目标的关系。

判断与执行步骤

  1. 复述原始目标。
  2. 拆成3-6个待验证问题。
  3. 标记每个问题需要的证据。
  4. 识别仍不明确的定义。
  5. 形成程序草案。
  6. 检查所有步骤是否回到目标。

常用资料 / 审计证据

  • 审计计划
  • 控制矩阵
  • 历史底稿仅作参考
  • 方法论
  • 项目负责人说明

应用场景

目标只有一句“验证离职用户是否及时停用”。在拿资料前先拆出HR总体、账号映射、离职日期、停用时间和离职后登录等验证点。

完成后应能回答

  • 目标和检查步骤有什么区别？
  • 一个目标怎样拆成可验证问题？
  • 哪些定义不确认会导致程序方向错误？

W1 · LEARNING 02

从风险与控制目标设计程序

WYX-M1-W1-L02

学习目标

能够先理解控制为什么存在，再决定测试哪些步骤。

核心内容

  • 风险描述可能发生的错误或未经授权行为。
  • 控制目标描述企业希望达到的状态。
  • 控制活动是客户实际采取的措施。
  • 审计程序用于验证控制设计和运行是否达到目标。
  • 程序不能因为去年检查某字段，今年也机械检查。
  • 控制方式变化时，程序应跟着企业实际调整。

判断与执行步骤

  1. 写风险。
  2. 写控制目标。
  3. 了解客户控制活动。
  4. 判断设计是否合理。
  5. 确定执行证据。
  6. 形成测试步骤。
  7. 明确异常后如何处理。

常用资料 / 审计证据

  • 制度/流程
  • 系统配置
  • 审批记录
  • 日志
  • 控制矩阵

应用场景

客户A通过HR邮件通知IT停用离职账号；客户B由HR系统自动触发AD停用。控制目标一致，但测试程序不会完全一样。

完成后应能回答

  • 控制目标和客户控制方式如何区分？
  • 为什么相同目标不代表相同程序？
  • 程序设计时哪些内容来自方法论，哪些来自客户实际？

W1 · LEARNING 03

资料需求从程序反推

WYX-M1-W1-L03

学习目标

能够根据每一步程序写出具体PBC，而不是等别人给资料清单。

核心内容

  • 总体资料用于定义和抽样，样本资料用于验证具体执行。
  • PBC应说明系统、期间、范围和需要字段。
  • 每份资料都要对应明确测试目的。
  • 不要只写“权限资料”“日志资料”。
  • 如果理想证据不存在，应提前考虑替代来源。
  • PBC顺序应考虑哪些资料会阻塞后续测试。

判断与执行步骤

  1. 列出程序步骤。
  2. 逐步写所需证据。
  3. 区分总体和样本。
  4. 补充系统/期间/字段。
  5. 识别替代资料。
  6. 按优先级形成PBC。

常用资料 / 审计证据

  • PBC清单
  • 程序草案
  • 系统清单
  • 字段样例
  • 客户资料

应用场景

验证应收账龄IPE，需要原始报表、查询参数、总账核对依据、关键字段来源，而不只是“请提供应收账龄表”。

完成后应能回答

  • 一个好的PBC至少包含什么？
  • 总体资料和样本证据有什么不同？
  • 什么资料应该优先要？

W1 · LEARNING 04

预期证据与证据边界

WYX-M1-W1-L04

学习目标

能够在执行前知道每份证据预计证明什么，并避免结论超过证据。

核心内容

  • 截图通常证明某时点状态。
  • 日志适合证明历史事件。
  • 制度证明要求，不证明执行。
  • 审批记录证明授权，不一定证明最终结果。
  • 系统报表可能需要IPE验证。
  • 如果预期证据拿不到，应决定补证、替代程序或缩小结论。

判断与执行步骤

  1. 为每一步写“要证明什么”。
  2. 确定最合适证据。
  3. 判断来源与期间。
  4. 取得证据后核对是否符合预期。
  5. 标记缺口。
  6. 决定补充程序。

常用资料 / 审计证据

  • 截图
  • 日志
  • 审批
  • 系统报表
  • 业务/财务资料

应用场景

客户提供当前账号已停用截图，不能直接支持“离职后1日内及时停用”，还需要历史停用时间或日志。

完成后应能回答

  • 为什么程序设计阶段就要想证据？
  • 什么是证据边界？
  • 证据形式与结论强度如何匹配？

W1 · LEARNING 05

异常后的进一步程序

WYX-M1-W1-L05

学习目标

能够在程序设计时预先考虑发现异常后应该验证什么，而不是遇到异常才完全停下。

核心内容

  • 异常可能是资料不足、正常业务原因、个别例外或控制缺陷。
  • 离职晚停用后应进一步看登录和操作。
  • Interface差异应追失败、重跑和最终落地。
  • IPE差异应确认查询口径、字段来源和导出后处理。
  • 程序应预留异常调查步骤。
  • 最终问题定性要建立在补充证据上。

判断与执行步骤

  1. 预设可能异常。
  2. 为异常列进一步程序。
  3. 确定补充证据。
  4. 量化范围/金额。
  5. 判断系统性。
  6. 形成结论边界。

常用资料 / 审计证据

  • 异常清单
  • 登录/操作日志
  • 接口日志
  • 业务/财务明细
  • 补偿控制

应用场景

抽样发现1个离职账号晚停用7天，下一步不是直接定性，而是检查期间登录、权限、操作和总体是否还有同类情况。

完成后应能回答

  • 为什么程序应该包含异常后动作？
  • 什么时候需要扩大样本？
  • 个别例外如何与系统性问题区分？

W1 · LEARNING 06

程序如何连接业务和财审

WYX-M1-W1-L06

学习目标

能够说明程序为什么重要，以及结果可能影响哪个业务、科目和认定。

核心内容

  • IT审计程序不是独立技术任务，需要连接财务报告相关风险。
  • 访问问题要看账号能影响什么业务数据或配置。
  • ITAC异常要看可能导致哪类交易错误。
  • Interface问题常影响完整性、准确性或截止。
  • IPE问题会影响财审选样、分析或控制复核。
  • 程序草案应至少有一句财审影响说明。

判断与执行步骤

  1. 识别系统涉及的业务流程。
  2. 识别主要财务科目。
  3. 判断潜在错报方向。
  4. 对应财报认定。
  5. 确认财审是否依赖相关控制/数据。
  6. 记录财审影响。

常用资料 / 审计证据

  • 业务流程
  • 财审重大科目
  • 风险清单
  • IT测试结果
  • 控制依赖

应用场景

WMS→ERP发货接口测试不是为了“证明接口正常”本身，而是因为它可能影响收入和成本完整性/截止。

完成后应能回答

  • 为什么程序需要连接财务影响？
  • IT问题和财务错报有什么区别？
  • 什么情况下需要及时和财审沟通？

W2 · LEARNING 01

方法论、模板与客户实际的关系

WYX-M1-W2-L01

学习目标

能够把方法论作为控制目标和最低要求，而不是把历史底稿当固定答案。

核心内容

  • 方法论定义审计目标、基本程序和证据要求。
  • 模板用于提高效率，但不能替代客户理解。
  • 客户流程、系统、组织架构和控制方式可能不同。
  • 复制程序前必须确认前提条件仍成立。
  • 模板中多余程序应删除，缺失程序应补充。
  • 最终底稿应反映本期客户实际，而不是上一项目名称替换。

判断与执行步骤

  1. 先看控制目标。
  2. 理解客户流程。
  3. 对照模板。
  4. 标记可复用部分。
  5. 标记需要删除/新增/调整部分。
  6. 记录调整依据。

常用资料 / 审计证据

  • 方法论
  • 历史模板
  • 客户制度/流程
  • 系统说明
  • 本期证据

应用场景

去年客户由IT手工停用离职账号，本期客户AD与HR自动同步。相同“离职停用”程序需要调整。

完成后应能回答

  • 模板最应该复用什么？
  • 什么情况下必须改变程序？
  • 怎样证明程序调整是有依据的？

W2 · LEARNING 02

相同控制目标，不同控制设计

WYX-M1-W2-L02

学习目标

能够比较两个客户如何用不同控制实现同一个目标。

核心内容

  • 控制目标可以相同，但控制活动可能是人工、自动或混合。
  • 自动控制重点可能转向配置、接口和ITGC。
  • 人工控制重点可能是频率、审批和执行证据。
  • 控制设计不同会影响总体和样本。
  • 补偿控制也会改变程序。
  • 评价应围绕是否达到目标，不围绕形式一致。

判断与执行步骤

  1. 写共同控制目标。
  2. 列客户A控制设计。
  3. 列客户B控制设计。
  4. 比较风险点。
  5. 调整程序和证据。
  6. 比较结论逻辑。

常用资料 / 审计证据

  • 控制流程
  • 系统配置
  • 审批/复核记录
  • 接口说明
  • 日志

应用场景

客户A每周人工复核高权限，客户B堡垒机实时限制并月度复核。两者控制目标相似但测试证据不同。

完成后应能回答

  • 什么叫“相同目标、不同设计”？
  • 自动控制和人工控制如何影响样本？
  • 控制形式不同能否直接说哪一个更好？

W2 · LEARNING 03

相同业务，不同系统架构

WYX-M1-W2-L03

学习目标

能够根据App、DB、SSO、SaaS等架构差异调整取证。

核心内容

  • 本地部署ERP与SaaS ERP责任边界不同。
  • SSO统一认证时，登录控制可能需要测试身份平台。
  • 数据库由客户管理或厂商托管，DB权限程序不同。
  • 第三方SaaS可能需要SOC报告或补偿控制。
  • 接口存在与否会改变数据可靠性测试。
  • 架构差异应先画清，再确定程序范围。

判断与执行步骤

  1. 画客户A技术关系。
  2. 画客户B技术关系。
  3. 识别责任边界。
  4. 识别关键系统依赖。
  5. 调整PBC。
  6. 调整测试程序。

常用资料 / 审计证据

  • 系统架构图
  • 合同/SLA/SOC
  • SSO配置
  • 管理员清单
  • 接口清单

应用场景

客户A本地ERP+SQL Server；客户B云ERP且数据库由厂商管理。不能照搬数据库账户和备份测试。

完成后应能回答

  • 系统架构为什么影响审计程序？
  • 第三方托管后客户还需要哪些控制？
  • 什么情况下需要重新判断Scope？

W2 · LEARNING 04

相同程序，不同证据形式

WYX-M1-W2-L04

学习目标

能够接受证据形式变化，但始终回到“能否支持同一审计目标”。

核心内容

  • 用户授权可能通过工单、邮件、OA或系统自动流程留证。
  • 测试证据可能是UAT文档、测试截图或业务确认记录。
  • 日志可来自应用、数据库、堡垒机或集中日志平台。
  • 没有固定模板不代表没有控制。
  • 证据可靠性仍需判断来源、期间、完整性。
  • 替代证据可以组合支持结论。

判断与执行步骤

  1. 明确待证明事项。
  2. 列客户实际证据。
  3. 判断每份证据证明力。
  4. 与标准证据要求对照。
  5. 补取缺口。
  6. 形成结论。

常用资料 / 审计证据

  • 工单
  • 邮件/OA
  • 系统日志
  • 测试记录
  • 第三方资料

应用场景

一个客户没有标准用户申请表，但权限开通必须走ServiceNow工单。测试重点应落在工单授权和实际权限，而不是坚持要纸质表。

完成后应能回答

  • 证据形式不同为什么不一定影响结论？
  • 什么情况下替代证据仍然不够？
  • 怎样避免“没看到模板=没控制”？

W2 · LEARNING 05

相似异常的财务影响可能不同

WYX-M1-W2-L05

学习目标

能够根据业务重要性、科目、权限和实际操作判断同类IT异常的风险差异。

核心内容

  • 同样是超级管理员，在低影响辅助系统和核心ERP中的风险不同。
  • 同样是Interface失败，影响收入接口和非财务通知接口的重要性不同。
  • 同样是账号晚停用，高权限且有实际操作比普通账号无登录风险高。
  • 同样是变更缺测试，收入计算逻辑与UI展示修改风险不同。
  • 异常迁移时应迁移判断框架，不迁移严重程度。
  • 财审依赖程度也是风险分层的重要因素。

判断与执行步骤

  1. 确认系统/业务重要性。
  2. 确认权限或异常性质。
  3. 确认实际操作。
  4. 确认财务科目/认定。
  5. 确认财审依赖。
  6. 重新评估风险等级。

  • 下一步建议应明确动作、责任人和预期结果。
  • 优先级需要随着新信息动态调整。

判断与执行步骤

  1. 列全部待办。
  2. 标财务/结论影响。
  3. 标截止时间。
  4. 标依赖关系。
  5. 选择Top 1-3。
  6. 提出具体推进动作。

常用资料 / 审计证据

  • 项目计划
  • 重大科目/Scope
  • PBC
  • Issue list
  • Review待办

应用场景

同时有弱密码、收入接口失败、备份保留不足和底稿格式问题。时间有限时应优先处理可能影响收入完整性的接口异常。

完成后应能回答

  • 为什么不能总按“容易做”排序？
  • 哪些因素决定优先级？
  • 下一步建议怎样写得可执行？

W4 · LEARNING 05

卡点与升级

WYX-M1-W4-L05

学习目标

能够在遇到真正阻塞时，先整理事实和方案，再向负责人升级。

核心内容

  • 卡点可能来自资料、技术、Scope、方法或客户争议。
  • 升级前应说明已经做了什么。
  • 明确卡点影响哪些结论和时间。
  • 最好提出一个或两个可选方案。
  • 不是所有不确定事项都需要立即升级。
  • 持续等待而不更新状态本身也是项目风险。

判断与执行步骤

  1. 定义卡点。
  2. 记录已尝试动作。
  3. 判断影响。
  4. 准备方案A/B。
  5. 明确需要负责人决定什么。
  6. 及时升级。
  7. 记录决定并执行。

常用资料 / 审计证据

  • 卡点记录
  • PBC
  • 技术分析
  • 负责人沟通
  • 项目计划

应用场景

无法验证某SaaS后台数据库权限，因为厂商不提供资料。升级时应说明已取得SOC/SLA情况、当前证据缺口和可选替代程序。

完成后应能回答

  • 什么才算需要升级的卡点？
  • 升级前最少准备哪些信息？
  • 怎样避免只说“这个做不了”？

W4 · LEARNING 06

模块状态汇报与主动建议

WYX-M1-W4-L06

学习目标

能够用5分钟或1页说明模块状态，并提出下一步建议。

核心内容

  • 状态汇报应先概括总体进度。
  • 突出关键已完成结论。
  • 只列真正重要的未决异常和PBC。
  • 说明每个卡点的影响。
  • 给出未来1-3天的优先动作。
  • 需要负责人支持的事项单独列出。
  • 主动建议应建立在项目状态理解上。

判断与执行步骤

  1. 写一句总体状态。
  2. 列关键完成项。
  3. 列高风险未决项。
  4. 列关键PBC/卡点。
  5. 提出下一步。
  6. 提出需要支持事项。
  7. 控制在1页。

常用资料 / 审计证据

  • 模块周报
  • PBC
  • Issue list
  • 计划
  • Review状态

应用场景

模块有10个测试、7个完成、2个待资料、1个待Review。汇报应突出哪个待资料会影响结论，而不是逐条念10个测试。

完成后应能回答

  • 项目负责人最需要知道什么？
  • 什么信息不需要放在状态汇报里？
  • 主动建议和单纯汇报有什么区别？
