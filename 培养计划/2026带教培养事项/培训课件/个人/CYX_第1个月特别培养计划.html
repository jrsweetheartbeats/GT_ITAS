W1 · LEARNING 01

业务事件与会计处理

CYX-M1-W1-L01

学习目标

能够从一笔业务的发生开始，逐步说明业务单据、系统状态、会计处理和最终财务报表影响。

核心内容

  • 销售业务通常经历订单、审核、发货/履约、开票、收入确认、应收确认和回款等环节。不同企业的收入确认触发点可能是发货、签收、验收或服务完成。
  • 采购业务通常经历采购申请、采购订单、收货/入库、发票、暂估/应付确认和付款。收货与发票往往不在同一天发生，因此需要理解暂估及后续冲回。
  • 系统中的业务单据并不等同于会计凭证。订单、出库单、入库单、发票等是业务事实的记录，会计凭证是对这些业务事实的财务反映。
  • 自动凭证通常由系统配置或业务事件触发；手工凭证由财务人员录入。两者的风险点、控制方式和审计证据不同。
  • 理解业务时至少要回答：谁发起、谁审核、系统记录什么、什么条件触发下一步、什么条件触发记账。
  • 理解会计处理时至少要回答：借贷方向、金额来源、确认时点、对应科目以及是否会产生跨期。

判断与执行步骤

  1. 先画出业务流程，不急于看控制。
  2. 标出每一步涉及的单据、系统和责任人。
  3. 确认哪一个业务状态会触发会计处理。
  4. 写出主要会计分录或至少明确受影响科目。
  5. 再判断该环节发生错误时，财务报表可能出现什么类型错报。
  6. 最后识别IT控制、人工控制和审计证据。

常用资料 / 审计证据

  • 销售订单、采购订单、出库单、入库单、发票、付款申请等业务单据。
  • 系统业务流程图、系统操作截图、状态字段说明。
  • 总账凭证、明细账、科目余额表。
  • 接口说明或自动记账配置。
  • 业务制度、会计政策、收入确认政策。

应用场景

客户订单已经审核，WMS显示已发货，但ERP第二天才生成收入凭证。需要分析业务事实、系统状态、会计确认时点以及是否存在截止风险。

完成后应能回答

  • 为什么“有销售订单”还不能直接说明收入已经实现？
  • 业务单据和会计凭证分别能证明什么？
  • 什么情况下需要特别关注月末前后的系统状态和入账日期？

W1 · LEARNING 02

财务报表认定

CYX-M1-W1-L02

学习目标

能够把发生、完整性、准确性、截止、权利义务、分类列报等认定用于具体项目判断。

核心内容

  • 发生/存在关注账上记录的交易或余额是否真实。例如账上记录了一笔销售，但实际上没有发货，主要涉及收入发生认定。
  • 完整性关注应记录的交易是否全部记录。例如WMS已发货但接口漏传ERP，可能导致收入和成本漏记。
  • 准确性关注金额、数量、价格、税率、汇率、计算逻辑是否正确。例如销售价格表配置错误可能影响收入准确性。
  • 截止关注交易是否记录在正确期间。例如12月31日后才发货，却在12月确认收入。
  • 权利义务关注资产和负债是否真正属于企业。例如寄售库存、受托代管库存可能影响存货权利义务。
  • 分类和列报关注会计处理是否落入正确账户和报表项目，例如费用被错误资本化为固定资产。

判断与执行步骤

  1. 先确认发生了什么业务错误或系统异常。
  2. 判断错误会造成多记、少记、金额错误、跨期还是归类错误。
  3. 将错误方向对应到一个或多个财务报表认定。
  4. 明确受影响的科目或披露。
  5. 再考虑财审可能追加什么程序。

常用资料 / 审计证据

  • 总账、明细账、业务明细。
  • 订单、物流、银行、发票等独立业务证据。
  • 期前期后交易清单。
  • 系统日志和接口记录。
  • 财务审计的重大科目及认定清单。

应用场景

OMS到ERP漏传100笔已发货订单，账面收入少记。核心关注点是收入完整性；如果漏传集中在12月31日前后，还要考虑截止。

完成后应能回答

  • 系统异常为什么通常不能只写“准确性”？
  • 什么情况下一个异常会同时影响完整性和截止？
  • 如何从“系统问题”进一步落到“财务错报可能是什么”？

W1 · LEARNING 03

收入与收款流程

CYX-M1-W1-L03

学习目标

掌握从订单到回款的完整数据链，能够识别收入确认、接口、自动控制和系统报表的审计关注点。

核心内容

  • 典型链路：客户下单 → 订单审核 → 发货/履约 → 签收/验收 → 开票 → 收入确认 → 应收账款 → 收款 → 核销。
  • 电商场景中常见系统包括OMS、WMS、ERP、支付平台；传统企业还可能有CRM、合同系统、开票系统。
  • 收入确认不一定以开票为准，应结合实际会计政策和履约条件。
  • 常见ITAC包括价格控制、折扣审批、信用额度、自动收入确认、自动开票、自动记账。
  • 常见Interface包括OMS→WMS、WMS→ERP、支付平台→ERP。
  • 常见IPE包括销售明细、未发货订单、应收账龄、回款明细、退款明细。
  • 收入审计常见风险包括虚构收入、漏记收入、金额错误、截止错误、退款或折让未及时处理。

判断与执行步骤

  1. 确认企业收入确认政策和系统触发条件。
  2. 画出订单、发货、记账和回款的数据流。
  3. 识别哪个系统保存原始业务事实，哪个系统形成会计记录。
  4. 检查关键接口和自动控制是否影响收入金额或时点。
  5. 确认财审使用哪些系统报表或明细。
  6. 将IT测试结果连接到收入相关财审程序。

常用资料 / 审计证据

  • 订单明细、发货/签收记录、ERP收入明细。
  • 接口批次记录、失败日志、重跑记录。
  • 价格表、折扣配置、收入确认配置。
  • 支付平台回款、银行流水、退款明细。
  • 财务收入确认政策和月末截止测试资料。

应用场景

OMS订单经WMS发货后自动传ERP确认收入。接口曾有失败批次，财务月末使用ERP收入明细做截止测试。需要同时考虑接口完整性、收入IPE和相关ITGC。

完成后应能回答

  • 收入确认触发点在哪里？
  • 接口失败会造成收入多记、少记还是跨期？
  • 财审使用ERP收入明细时，为什么还需要验证明细完整性？

W1 · LEARNING 04

采购、存货与应付

CYX-M1-W1-L04

学习目标

掌握采购、入库、暂估、应付和付款之间的关系，理解库存数量、库存金额和成本结转的系统依赖。

核心内容

  • 采购流程通常为采购申请 → 采购订单 → 收货/入库 → 发票 → 应付确认 → 付款。
  • 收货早于发票时可能产生暂估；发票到达后需要冲回暂估并按实际金额入账。
  • 存货数量通常来自WMS/ERP库存模块；存货金额来自计价逻辑、采购成本、生产成本等。
  • 制造企业还需要理解领料、完工入库、在制品、成本归集和成本结转。
  • 三单匹配常用于控制采购订单、收货记录和供应商发票的一致性。
  • 接口失败、手工调整、负库存、异常成本等都可能影响存货和成本。
  • 存货相关常见认定包括存在、完整性、准确性/计价、截止和权利义务。

判断与执行步骤

  1. 先明确采购、收货、发票、付款由哪些系统记录。
  2. 确认存货数量和金额分别从哪里产生。
  3. 识别暂估、冲回、成本结转等关键系统处理。
  4. 识别三单匹配、价格校验等ITAC。
  5. 关注WMS与ERP之间的入库、出库、库存接口。
  6. 将异常对应到存货、成本、应付等科目和认定。

常用资料 / 审计证据

  • 采购订单、入库单、供应商发票。
  • WMS库存明细、ERP库存台账。
  • 三单匹配配置、容差配置。
  • 暂估明细、成本计算表、月末结转记录。
  • 接口日志、手工调整清单、负库存清单。

应用场景

WMS显示100件已入库，ERP只收到80件，财务月底按ERP库存计价。需要分析接口失败是否导致存货数量/金额少记，以及应付暂估是否同步受影响。

完成后应能回答

  • 为什么库存数量正确不代表库存金额一定正确？
  • 采购三单匹配主要解决什么风险？
  • WMS与ERP库存差异可能影响哪些科目？

W1 · LEARNING 05

资金与付款系统链路

CYX-M1-W1-L05

学习目标

理解从付款申请到银行执行和会计记账的完整链路，能够区分授权、执行和记录三个层面的控制。

核心内容

  • 付款流程通常包含付款申请、审批、付款指令生成、银行执行、付款结果返回和会计记账。
  • OA可以承载审批，但真正发起付款指令的系统可能是ERP、银企直联或网银。
  • 付款审批通过不代表付款一定正确，还要关注收款账号、金额、币种和最终银行执行结果。
  • 供应商银行账号等主数据属于高风险字段，修改权限和修改审批需要关注。
  • 常见ITAC包括金额阈值审批、付款批次审批、重复付款校验、银行账号校验。
  • 银企直联接口或文件传输需要关注完整性、重复发送、失败重传和回执。
  • 资金相关财审通常关注未经授权付款、重复付款、错误账户、账实不符等风险。

判断与执行步骤

  1. 识别付款申请、审批、付款和记账分别在哪个系统。
  2. 确认谁能新增/修改收款账号。
  3. 确认系统如何根据金额、类型触发审批。
  4. 确认银行指令如何生成并发送。
  5. 获取最终银行回执或流水，验证系统审批与实际付款一致。
  6. 将异常与货币资金、应付账款等科目连接。

常用资料 / 审计证据

  • 付款申请、OA审批轨迹。
  • 供应商主数据及银行账号修改日志。
  • 银企直联付款批次、银行回执。
  • 网银流水、银行对账单。
  • 付款凭证、应付核销记录。

应用场景

采购人员可以修改供应商银行账号，付款申请经OA审批后自动推送银企直联。需要验证账号修改控制、付款审批和最终付款账户是否一致。

完成后应能回答

  • 审批截图能证明什么，不能证明什么？
  • 为什么供应商银行账号修改权限属于高风险权限？
  • 系统付款成功后还要核对哪些会计记录？

W1 · LEARNING 06

ITGC、ITAC、Interface、IPE的关系

CYX-M1-W1-L06

学习目标

能够在同一业务流程中准确区分四类审计对象，并说明它们之间的依赖关系。

核心内容

  • ITGC关注系统环境能否持续支持应用和数据可靠运行，主要包括访问、变更、运维和备份等。
  • ITAC嵌入具体业务处理，例如自动审批、自动计算、自动校验、自动限制。
  • Interface关注系统之间数据传输的完整性和准确性。
  • IPE是控制或审计程序使用的系统生成信息，例如应收账龄表、销售明细、库存报表。
  • 一个ITAC可能依赖主数据、参数、接口和ITGC。
  • 一份IPE可能由多个系统数据拼接产生，因此可能依赖接口。
  • 如果相关ITGC无法依赖，财审对ITAC或IPE的依赖程度可能需要重新评估。

判断与执行步骤

  1. 先确认业务流程和财务审计目的。
  2. 识别关键自动控制和关键报表。
  3. 识别关键数据是否经过接口。
  4. 识别控制和数据依赖的应用及基础ITGC。
  5. 分别设计ITGC、ITAC、Interface和IPE测试。
  6. 最后综合评价是否足以支持财审依赖。

常用资料 / 审计证据

  • 系统控制配置、参数表。
  • 接口设计文档、批次日志。
  • 系统报表、查询条件、字段说明。
  • 用户权限、程序变更、运维日志等ITGC证据。
  • 财审拟依赖控制或报表的说明。

应用场景

ERP根据WMS发货数据自动确认收入，财务每月使用ERP销售明细做收入复核。该流程同时涉及WMS→ERP Interface、自动收入确认ITAC、销售明细IPE和相关ITGC。

完成后应能回答

  • 同一个流程为什么可能同时需要测试四类对象？
  • ITAC有效为什么还需要考虑ITGC？
  • IPE与普通系统截图有什么区别？

W2 · LEARNING 01

财务报告相关系统

CYX-M1-W2-L01

学习目标

能够根据系统是否产生、处理、存储、传输或控制重大财务信息判断是否进入Scope。

核心内容

  • 系统直接生成总账、明细账、收入、采购、库存、工资等财务数据时，通常与财务报告相关。
  • 系统不直接记账，但承载关键业务事实时，也可能相关，例如WMS决定库存数量、MES决定生产成本基础数据。
  • 系统承载关键自动控制时，即使不保存最终会计记录，也可能影响财审依赖。
  • 系统生成关键IPE时，也可能需要纳入相关测试。
  • 系统只是沟通、文档存储或低风险辅助工具时，通常不直接进入财务报告Scope，但要结合实际用途。
  • Scope结论需要写清纳入/不纳入理由，而不是只填Yes/No。

判断与执行步骤

  1. 识别重大账户和业务循环。
  2. 列出参与这些流程的所有系统。
  3. 逐个确认系统处理什么数据、执行什么控制、生成什么报表。
  4. 判断系统对财务报告是否有直接或间接影响。
  5. 记录纳入/不纳入结论及依据。
  6. 列出仍需向财审或客户确认的信息。

常用资料 / 审计证据

  • 系统清单、系统架构图。
  • 业务流程图、RACM。
  • 重大科目及财审风险清单。
  • 关键ITAC和IPE清单。
  • 系统功能说明、访谈记录。

应用场景

CRM只做客户跟进时可能不纳入；若CRM直接生成销售订单并传ERP，则需要重新判断其对收入流程的影响。

完成后应能回答

  • 什么情况下一个业务系统虽然不记账也要纳入？
  • 为什么“核心系统”不是充分的Scope判断依据？
  • 不纳入Scope时需要保留哪些判断依据？

W2 · LEARNING 02

重大业务流程与系统范围

CYX-M1-W2-L02

学习目标

能够从重大业务流程反推系统范围，而不是先从IT系统清单出发。

核心内容

  • 重大业务流程通常围绕重大账户和重大交易类别展开，例如收入、采购、存货、资金、工资、固定资产。
  • 每个流程需要识别发起、授权、处理、记录、报告等关键步骤。
  • 同一流程可能跨多个系统，例如CRM→OMS→WMS→ERP。
  • 同一系统可能同时支持多个流程，例如ERP同时支持采购、销售、存货、总账。
  • 外围系统往往保存更接近原始业务事实的数据，不能只关注最终ERP。
  • Scope判断应与财审的重大账户、重大错报风险和计划依赖保持一致。

判断与执行步骤

  1. 先拿到财审重大科目和业务循环。
  2. 逐个流程画出系统链路。
  3. 确认每个系统处理的数据和控制。
  4. 确认最终财务数据从哪里产生。
  5. 识别是否有关键系统被遗漏。
  6. 与财审确认依赖范围。

常用资料 / 审计证据

  • 财审计划、重大科目清单。
  • 业务流程图、访谈记录。
  • 系统架构图、接口清单。
  • RACM、控制矩阵。
  • 财务与业务系统字段或报表。

应用场景

制造企业收入由CRM录单、WMS发货、ERP记账。虽然ERP形成会计凭证，CRM和WMS也可能因关键业务数据和接口进入范围。

完成后应能回答

  • 如何从收入流程反推系统Scope？
  • 为什么只审ERP可能不够？
  • 怎样识别外围系统是否影响财务报告？

W2 · LEARNING 03

ITAC对Scope的影响

CYX-M1-W2-L03

学习目标

能够根据关键自动控制所在系统及其依赖关系判断Scope。

核心内容

  • 关键ITAC包括自动计算、自动审批、自动限制、自动匹配和自动记账。
  • 如果财审计划依赖某项ITAC，该ITAC所在应用需要纳入相关评估。
  • ITAC可能依赖主数据、配置参数、上游系统数据和接口。
  • 例如ERP信用控制依赖CRM客户主数据时，CRM可能成为相关系统。
  • ITAC的逻辑或配置由谁修改，会影响相关访问和变更控制范围。
  • 不能因为系统存在自动控制就自动纳入，要确认该控制是否与重大财务报告风险相关。

判断与执行步骤

  1. 识别财审或业务控制活动计划依赖的ITAC。
  2. 确认ITAC所在系统。
  3. 识别其输入、主数据和参数来源。
  4. 确认上游系统和接口。
  5. 识别配置变更和访问权限。
  6. 形成Scope结论。

常用资料 / 审计证据

  • ITAC清单。
  • 系统配置、参数截图。
  • 主数据维护流程。
  • 接口设计说明。
  • 相关财审控制依赖说明。

应用场景

ERP信用额度控制依赖CRM维护的客户信用额度。若该控制用于降低应收风险，需要进一步评估CRM和相关接口。

完成后应能回答

  • ITAC为什么可能把上游系统带入Scope？
  • 参数维护系统和执行控制的系统不一致时怎么判断？
  • 哪些ITAC虽然存在，但不一定对财务报告重要？

W2 · LEARNING 04

IPE对Scope的影响

CYX-M1-W2-L04

学习目标

能够从财审或业务控制使用的系统报表反推相关系统和数据来源。

核心内容

  • IPE可以用于控制执行，例如财务每月用异常交易报表复核；也可以直接用于审计程序，例如函证选样、截止测试。
  • 需要确认报表来自哪个系统、哪个功能、什么查询条件。
  • 报表可能依赖多个底层表或上游系统数据。
  • 报表完整性和准确性要与其使用目的匹配。
  • 导出后人工增加字段、筛选、公式或调整会增加可靠性风险。
  • 如果财审高度依赖一份关键报表，相关系统和报表生成逻辑需要纳入考虑。

判断与执行步骤

  1. 明确报表被谁用于什么目的。
  2. 确认报表来源系统和查询条件。
  3. 追溯关键字段和底层数据来源。
  4. 确认是否经过接口或二次加工。
  5. 判断是否存在手工修改。
  6. 确定系统和相关ITGC范围。

常用资料 / 审计证据

  • 报表原始导出文件。
  • 查询参数和系统截图。
  • 字段说明、报表逻辑。
  • 总账/独立数据核对。
  • 导出后处理记录。

应用场景

财审使用ERP应收账龄表选函证样本并做减值分析。需要评估ERP、账龄计算逻辑、关键字段和相关ITGC。

完成后应能回答

  • IPE为什么不只是“系统导出的Excel”？
  • 一份报表总额对上总账是否足够？
  • 哪些手工处理会影响报表可靠性？

W2 · LEARNING 05

Interface对Scope的影响

CYX-M1-W2-L05

学习目标

能够判断关键财务数据经过系统接口传输时，源系统、目标系统和接口程序是否相关。

核心内容

  • 接口测试关注数据从源系统到目标系统的完整性和准确性。
  • 需要了解传输方式、频率、触发条件、字段映射和异常处理。
  • 源系统数据本身必须可靠，否则目标系统“传输完整”也不能解决源数据错误。
  • 接口失败后可能重跑、补传、人工补录或丢弃，需要关注实际处理方式。
  • 接口Mapping或程序变更可能改变会计数据，因此要考虑变更控制。
  • 关键接口两端系统通常都要结合财务影响判断范围。

判断与执行步骤

  1. 识别源系统和目标系统。
  2. 确认传输的关键业务字段。
  3. 确认触发频率和传输方式。
  4. 了解失败、重跑、异常队列和人工补录。
  5. 判断源系统数据是否可靠。
  6. 将接口影响对应到财务科目和认定。

常用资料 / 审计证据

  • 接口文档、字段Mapping。
  • 批次日志、失败日志。
  • 源系统与目标系统明细。
  • 重跑记录、异常队列。
  • 接口程序变更记录。

应用场景

WMS每天把出库数据传ERP并触发成本结转。接口失败可能造成存货和成本错报，因此WMS、ERP及接口本身都需要评估。

完成后应能回答

  • 接口记录数一致是否足够？
  • 为什么需要验证源系统数据？
  • 人工补录接口失败数据时需要关注什么？

W2 · LEARNING 06

第三方SaaS、Excel和小工具

CYX-M1-W2-L06

学习目标

能够识别低技术复杂度但可能具有重大财务影响的工具和第三方系统。

核心内容

  • Excel宏、Access、本地脚本可能承担收入确认、成本分摊、税费计算等关键财务逻辑。
  • 第三方SaaS可能承载工资、库存、支付、报销或销售数据。
  • 是否进入范围取决于财务报告依赖，不取决于是否由IT部门管理。
  • 缺少正式ITGC时，需要考虑访问、变更、版本、公式保护、输入输出核对等替代控制。
  • 第三方系统还需要考虑合同、SLA、SOC报告或客户自身补偿控制。
  • 文件上传下载、手工复制粘贴和宏运行是常见风险点。

判断与执行步骤

  1. 确认工具处理的业务和金额。
  2. 确认输入数据来源。
  3. 确认计算或处理逻辑。
  4. 确认谁可修改公式、脚本或参数。
  5. 确认输出如何进入正式财务系统。
  6. 决定采用何种测试和补偿控制评价。

常用资料 / 审计证据

  • Excel原文件、公式、宏代码。
  • 版本记录、访问权限。
  • 输入明细、输出结果。
  • 上传ERP记录。
  • 第三方合同、SOC报告或服务说明。

应用场景

3人使用的Excel宏每月计算8000万元收入确认金额并上传ERP。虽然不是正式应用系统，仍然需要关注其输入完整性、计算逻辑和修改控制。

完成后应能回答

  • Excel为什么可能成为关键财务报告工具？
  • 只检查公式是否正确是否足够？
  • 第三方SaaS没有SOC报告时还能怎么取得证据？

W3 · LEARNING 01

风险与控制目标

CYX-M1-W3-L01

学习目标

能够先明确风险，再定义控制目标，避免直接从检查步骤开始。

核心内容

  • 业务风险描述业务可能发生的不利事件；财务报告风险描述可能造成的错报；IT风险描述系统层面的原因或条件。
  • 控制目标要明确希望控制达到什么状态，例如“仅授权用户能够访问系统并执行与职责相符的功能”。
  • 控制活动是实现控制目标的具体方式，例如经理审批、系统限制、定期复核。
  • 测试程序用于验证控制设计和执行是否有效，不应与控制活动混为一谈。
  • 同一风险可以有多种控制；同一控制也可能应对多个风险。
  • 程序设计必须能够回到风险和控制目标解释其必要性。

判断与执行步骤

  1. 写出可能发生的错误或未经授权行为。
  2. 判断该错误是否可能影响重大财务信息。
  3. 形成控制目标。
  4. 识别企业现有控制活动。
  5. 评价控制设计是否覆盖风险。
  6. 再设计具体测试程序。

常用资料 / 审计证据

  • 制度、流程说明。
  • 控制矩阵/RACM。
  • 系统配置和权限。
  • 审批、复核记录。
  • 异常或违规记录。

应用场景

离职人员账号未及时停用。风险不只是“账号没关”，而是未经授权访问可能造成交易或数据被修改。控制目标应围绕离职用户及时失去访问权限。

完成后应能回答

  • 风险、控制目标、控制活动和测试程序分别是什么？
  • 为什么不能直接把制度条款复制成控制目标？
  • 一个IT问题如何连接到财务报告风险？

W3 · LEARNING 02

设计有效性与执行有效性

CYX-M1-W3-L02

学习目标

能够分别评价控制设计是否合理，以及控制在审计期间是否持续按设计执行。

核心内容

  • 设计有效性关注控制本身是否足以预防或发现相关风险。
  • 执行有效性关注控制是否在审计期间按要求执行。
  • 设计有缺陷时，即使偶尔执行也不能完全解决风险。
  • 控制设计合理但有少量执行偏差，需要进一步判断偏差性质、频率和影响。
  • 期末配置截图只能证明某一时点状态，不能单独证明全年持续有效。
  • 访谈可以帮助理解流程，但通常需要其他证据证明实际执行。

判断与执行步骤

  1. 明确控制目标。
  2. 了解控制活动的设计和责任人。
  3. 判断设计是否覆盖关键风险。
  4. 确定控制频率和审计期间。
  5. 取得期间执行证据。
  6. 发现例外后判断是设计问题还是执行问题。

常用资料 / 审计证据

  • 流程制度、系统配置。
  • 全年执行记录、审批记录。
  • 日志、变更历史。
  • 访谈纪要。
  • 异常说明和补偿控制证据。

应用场景

制度规定离职1日内停用账号，但实际没有HR自动通知机制，仅由IT每月手工清理。需要先评价设计是否足以实现及时停用。

完成后应能回答

  • 什么证据能证明设计，什么证据能证明执行？
  • 为什么期末截图不能证明全年有效？
  • 个别执行偏差和设计缺陷的处理有什么区别？

W3 · LEARNING 03

总体、期间与样本

CYX-M1-W3-L03

学习目标

能够定义正确的总体，验证总体完整性，并根据控制频率和审计目的选择适当样本。

核心内容

  • 总体必须覆盖审计期间内所有相关控制执行对象，例如全年所有新增用户、所有程序变更。
  • 客户提供的样本清单不能直接视为总体，需要了解生成方式并验证完整性。
  • 控制频率决定样本策略：持续自动控制与每月人工复核的测试方式不同。
  • 样本量通常应遵循方法论，并结合控制频率、依赖程度和风险。
  • 自动控制如果逻辑和ITGC稳定，通常不需要像人工控制一样大量抽样。
  • 发现例外后要评估原因、是否具有系统性、是否需要扩大样本。

判断与执行步骤

  1. 明确审计期间。
  2. 定义总体对象和控制频率。
  3. 确认总体来源。
  4. 验证总体完整性。
  5. 确定样本量和抽样方法。
  6. 记录样本理由并处理例外。

常用资料 / 审计证据

  • 系统导出的全年清单。
  • 总账/日志/工单等独立完整性依据。
  • 样本选择记录。
  • 抽样方法和方法论。
  • 异常样本补充资料。

应用场景

全年有86个程序变更，客户只提供10个“代表性变更”。需要先获取并验证全年总体，再进行样本选择。

完成后应能回答

  • 总体是什么？
  • 如何证明总体完整？
  • 发现1个异常后什么时候需要扩大测试？

W3 · LEARNING 04

审计证据的充分性和适当性

CYX-M1-W3-L04

学习目标

能够判断现有材料是否足以支持结论，并明确还缺什么证据。

核心内容

  • 充分性主要关注证据数量、期间和覆盖程度；适当性主要关注证据的相关性和可靠性。
  • 系统原生日志通常比人工整理Excel更可靠，但仍需确认日志来源和完整性。
  • 截图适合证明某时点配置；历史操作通常需要日志或审计轨迹。
  • 审批记录证明授权过程，不一定证明实际交易结果。
  • 第三方证据、银行证据、外部系统数据通常具有更高独立性。
  • 多类证据相互印证可以增强结论可靠性。

判断与执行步骤

  1. 先明确要证明的具体结论。
  2. 判断现有证据与该结论是否直接相关。
  3. 判断证据来源、生成过程和完整性。
  4. 判断时间范围是否覆盖审计期间。
  5. 识别证据缺口。
  6. 补充不同来源证据或缩小结论范围。

常用资料 / 审计证据

  • 系统日志、审计轨迹。
  • 审批记录、工单。
  • 原始系统导出文件。
  • 第三方/银行资料。
  • 配置截图、制度文件。

应用场景

客户提供截图显示账号已Disable，但无法看到具体停用日期。该截图只能证明当前状态，不能证明是否按要求及时停用。

  • 资料不足时如何写当前结论？

W4 · LEARNING 01

规则命中与审计异常

CYX-M1-W4-L01

学习目标

能够理解数据筛选结果只是风险线索，需要进一步核验后才能形成审计问题。

核心内容

  • 规则命中只说明记录满足筛选条件，例如“离职后仍Active”“月末有反审核”，不能直接证明发生了控制失效或财务错报。
  • 命中结果可能来自正常业务原因、时间差、数据质量、历史遗留或规则设计过宽。
  • 需要先验证总体完整性和字段含义，再确认每类命中的真实原因。
  • 可以根据金额、权限、频率、业务重要性等指标给命中结果分层。
  • 高风险命中优先核验，低风险命中可以抽样或汇总分析。
  • 最终问题描述必须基于已验证事实，而不是规则条件本身。

判断与执行步骤

  1. 确认规则逻辑和数据字段。
  2. 验证命中总体是否完整。
  3. 对命中结果分层。
  4. 抽取代表性或高风险记录核验。
  5. 确认实际业务原因和系统操作。
  6. 判断是否形成控制偏差、问题或仅为数据例外。

常用资料 / 审计证据

  • 规则脚本/筛选逻辑。
  • 命中明细和总体。
  • HR、权限、日志、业务单据。
  • 金额和交易结果。
  • 客户解释及支持证据。

应用场景

筛出42个离职后仍Active账号。需要进一步确认离职日期、账号状态变化、期间登录和实际操作，再判断是否存在未授权访问风险。

完成后应能回答

  • 规则命中为什么不能直接等于问题数量？
  • 如何对异常结果分层？
  • 什么证据可以把“Active”进一步验证到“实际使用”？

W4 · LEARNING 02

异常类型与定性

CYX-M1-W4-L02

学习目标

能够区分资料不足、个别例外、执行偏差和设计缺陷，并根据证据强度控制结论表述。

核心内容

  • 资料不足表示现有证据无法完成评价，需要继续取证，不能直接判缺陷。
  • 个别例外可能是控制总体有效情况下的孤立偏差，需要结合频率和原因判断。
  • 执行缺陷表示控制设计合理，但实际未按要求运行。
  • 设计缺陷表示控制本身不足以应对风险，即使按设计执行也可能无法达到控制目标。
  • 补偿控制可能降低最终风险，但需要实际测试。
  • 结论还要考虑异常数量、金额、权限、期间和财审依赖。

判断与执行步骤

  1. 整理已知事实。
  2. 确认制度/控制设计。
  3. 判断现有证据是否足够。
  4. 归类异常性质。
  5. 识别补偿控制。
  6. 评估对财审依赖和进一步程序的影响。

常用资料 / 审计证据

  • 制度和流程。
  • 控制执行证据。
  • 异常样本明细。
  • 补偿控制证据。
  • 财务影响分析。

应用场景

10个变更样本中1个缺测试记录，客户解释为紧急变更。需要确认紧急变更制度、事后审批、影响范围和是否有补偿性复核。

完成后应能回答

  • 资料未提供与控制未执行有什么区别？
  • 个别例外什么时候可能导致控制不能依赖？
  • 怎样识别设计缺陷？

异常证据链

CYX-M1-W4-L03

学习目标

能够围绕一个清晰问题组织多来源证据，形成Reviewer可以直接复核的判断链路。

核心内容

  • 事实层：谁、何时、在哪个系统、做了什么、数量和金额是多少。

  • 证据层：系统日志、权限、HR、业务单据、财务记录等是否互相支持。
  • 影响层：异常是否改变业务结果、系统数据或会计记录。

判断与执行步骤

  1. 用一句话写明异常事实。
  2. 列出控制要求。
  3. 按来源整理证据。
  4. 追踪实际业务和财务结果。
  5. 识别证据缺口。
  6. 形成初步结论和后续行动。

常用资料 / 审计证据

  • 权限表、日志。
  • HR离职信息。
  • 业务单据、审批。
  • 凭证历史、财务结果。
  • 补偿控制记录。

应用场景

超级管理员在月末修改一笔会计凭证。需要结合管理员权限、操作日志、凭证修改历史、业务审批及最终财务结果判断。

完成后应能回答

  • 证据链中哪一环缺失会影响结论？

  • 技术操作如何继续追到财务影响？

W4 · LEARNING 04

风险分层与测试优先级

CYX-M1-W4-L04

学习目标

能够在项目时间有限时优先处理最可能影响审计结论的事项。

核心内容

  • 优先级应综合财务金额、权限强度、异常性质、发生频率和财审依赖程度。
  • 涉及收入、资金、存货等重大科目的关键ITAC、接口和IPE通常优先于低影响配置问题。
  • 高权限账号实际发生操作时优先级高于“仅存在账号但无操作”。
  • 异常可能影响财审控制依赖时，需要及时升级。
  • 低风险事项可以记录并后续跟进，不应占用过多项目时间。
  • 优先级需要在状态表中体现，避免所有事项同时推进。

判断与执行步骤

  1. 列出全部未完成事项。
  2. 标记财务影响和审计依赖。
  3. 评估发生可能性和异常性质。
  4. 分为高/中/低优先级。
  5. 先处理会改变审计结论的事项。
  6. 定期更新优先级。

常用资料 / 审计证据

  • 问题清单。
  • PBC状态。
  • 重大科目及风险。
  • 财审依赖清单。
  • 异常金额和数量。

同一项目同时存在弱密码、5个离职账号、收入接口失败、备份保留7天、IT经理超管。只有1天时，需要先处理最可能影响重大财务数据和财审依赖的事项。
