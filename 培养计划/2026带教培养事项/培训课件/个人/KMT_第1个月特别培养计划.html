W1 · LEARNING 01

采购入库、暂估与应付

KMT-M1-W1-L01

学习目标

能够理解采购订单、收货入库、暂估应付、发票和正式应付之间的关系，并判断系统异常可能造成的会计影响。

核心内容

  • 采购申请和采购订单属于业务授权与交易条件记录，通常不会直接形成会计凭证。
  • 收货或入库表示企业已经取得货物，是存货数量增加以及暂估负债判断的重要依据。
  • 货已收到但发票未到时，企业可能根据订单价格、标准价或其他规则形成暂估应付。
  • 发票到达后需要与采购订单、收货记录匹配，并冲回暂估、确认正式应付。
  • 入库、暂估、发票、付款可能分别发生在不同期间，因此需要关注期末完整性和截止。
  • WMS、SRM、ERP之间的数据流可能影响存货数量、暂估金额和应付账款。

判断与执行步骤

  1. 先确认采购、收货、入库、发票分别由哪个系统处理。
  2. 明确哪一个事件触发存货增加和暂估。
  3. 确认暂估金额的取值规则。
  4. 确认发票到达后的匹配和冲回逻辑。
  5. 检查月末收货未开票清单及跨期发票。
  6. 将系统异常对应到存货、应付、成本及相关认定。

常用资料 / 审计证据

  • 采购订单、入库单、收货单。
  • 期末收货未开票清单。
  • 暂估明细和冲回记录。
  • 供应商发票。
  • WMS/ERP接口记录和会计凭证。

应用场景

12月28日货物已入库，1月5日收到发票。ERP在12月自动暂估100万元，1月冲回后按98万元确认正式应付。需要判断暂估、冲回和价差处理是否正确。

完成后应能回答

  • 为什么入库和发票不在同一天会影响期末审计？
  • 暂估少记会主要影响什么科目和认定？
  • 暂估金额来源错误会造成什么类型错报？

W1 · LEARNING 02

销售、发货、收入与应收

KMT-M1-W1-L02

学习目标

能够理解收入从订单、履约到会计确认的完整链路，并识别收入发生、完整性、准确性和截止风险。

核心内容

  • 销售订单只说明客户购买意向或合同安排，不等于收入已经实现。
  • 收入确认通常依赖发货、签收、验收、服务完成等履约事实，具体触发点取决于企业会计政策。
  • 系统可能根据WMS发货状态、物流签收或人工确认自动生成收入和应收。
  • 价格、折扣、数量、币种、税率和确认日期都是影响收入准确性的关键字段。
  • 收入接口漏传可能造成少记；提前标记发货可能造成多记或跨期。
  • 退款、折让和取消订单需要关注后续是否及时冲减收入和应收。

判断与执行步骤

  1. 确认收入确认政策。
  2. 画出订单、发货、签收、记账和回款系统链路。
  3. 识别收入确认触发字段。
  4. 确认价格和折扣来源。
  5. 识别自动记账和接口。
  6. 将异常映射到收入、应收、成本和认定。

常用资料 / 审计证据

  • 销售订单、发货单、签收记录。
  • ERP收入和应收明细。
  • 价格表、折扣审批。
  • 退款/折让明细。
  • 物流、支付平台和接口数据。

应用场景

ERP根据WMS“已发货”状态自动确认收入。12月31日部分订单被标记已发货，但物流记录显示1月2日才实际出库。需要重点判断发生和截止。

完成后应能回答

  • 为什么系统状态需要和真实业务事实交叉验证？
  • 收入漏传和提前确认分别影响哪些认定？
  • 收入自动记账可能涉及哪些ITAC和Interface？

W1 · LEARNING 03

资金支付、审批与银行执行

KMT-M1-W1-L03

学习目标

能够区分付款授权、系统执行和会计记录三个环节，并理解每类证据能证明什么。

核心内容

  • 付款申请说明业务部门或财务提出付款需求。
  • 审批流程用于确认付款经过适当授权，但审批通过不代表最终付款账户和金额一定正确。
  • 银企直联或网银负责实际向银行发送付款指令。
  • 供应商银行账号、付款金额、币种和收款方是资金流程关键字段。
  • 系统付款结果需要与银行回执、银行流水和会计凭证核对。
  • 供应商主数据修改权限和付款权限通常属于高风险权限。

判断与执行步骤

  1. 确认付款申请在哪个系统。
  2. 确认审批路径和金额阈值。
  3. 确认收款账户从哪里取值。
  4. 确认付款指令如何发送银行。
  5. 核对银行实际执行结果。
  6. 追踪付款结果到会计凭证和应付核销。

常用资料 / 审计证据

  • 付款申请、审批轨迹。
  • 供应商主数据及修改日志。
  • 银企直联批次和银行回执。
  • 银行流水、对账单。
  • 会计凭证、应付核销记录。

应用场景

付款已在OA审批通过，但供应商银行账号在付款前一天被修改。需要验证账号修改授权、付款指令最终账户和银行实际付款结果。

完成后应能回答

  • 审批记录、银行回执、会计凭证分别证明什么？
  • 客户说“付款没损失”是否足以说明控制没有问题？
  • 供应商银行账号修改为什么要单独关注？

W1 · LEARNING 04

财务报表认定在项目中的应用

KMT-M1-W1-L04

学习目标

能够根据具体错误方向判断财务报表认定，而不是只记定义。

核心内容

  • 发生/存在：账上记录的交易或余额是否真实，例如未发货却确认收入。
  • 完整性：应记录的交易是否全部记录，例如接口漏传已发货订单。
  • 准确性/计价：金额、数量、价格、成本、汇率等是否正确。
  • 截止：交易是否记录在正确会计期间，尤其关注月末和年末。
  • 权利义务：资产或负债是否真实归属于企业，例如寄售、受托库存。
  • 分类与列报：会计记录是否进入正确科目和报表项目。

判断与执行步骤

  1. 先描述业务或系统异常。
  2. 判断它可能导致多记、少记、金额错误、跨期还是归类错误。
  3. 确定受影响科目。
  4. 对应主要财务报表认定。
  5. 判断财审可能增加什么程序。
  6. 将IT测试与财审目的连接。

常用资料 / 审计证据

  • 财审重大科目和风险清单。
  • 总账、明细账。
  • 业务单据。
  • 系统日志和接口记录。
  • 会计政策。

应用场景

WMS向ERP漏传一批12月已发货订单，导致收入未入账。主要涉及收入完整性；如果1月才补记，还需要考虑截止。

完成后应能回答

  • 为什么很多IT异常不能一律写“准确性”？
  • 一个异常什么时候会同时影响多个认定？
  • 如何从IT异常落到财审程序？

W1 · LEARNING 05

业务系统、财务系统与会计结果

KMT-M1-W1-L05

学习目标

能够理解业务系统记录业务事实，财务系统形成会计结果，外围系统和接口可能共同影响财务数据。

核心内容

  • ERP可能既是业务系统也是财务系统，但企业常常还有CRM、WMS、MES、OA、银企直联等外围系统。
  • 外围系统可能保存更接近原始业务事实的数据，例如WMS发货、MES完工。
  • 财务系统最终形成总账和财务报表，但上游数据错误会被传递到会计记录。
  • Interface负责在系统间传输数据，失败、重跑、人工补录都会影响最终结果。
  • IPE是财审或控制活动依赖的系统生成信息，例如销售明细、库存明细、账龄表。
  • ITGC、ITAC、Interface、IPE通常需要放在同一业务链路中理解。

判断与执行步骤

  1. 从业务流程识别所有系统。
  2. 标记原始业务事实在哪个系统产生。
  3. 标记数据如何进入ERP或总账。
  4. 识别自动控制、接口和关键报表。
  5. 确认财审使用哪些数据或控制。
  6. 明确相关ITGC依赖。

常用资料 / 审计证据

  • 系统架构图。
  • 业务流程图。
  • 接口清单。
  • 系统报表。
  • 财审依赖清单。

应用场景

WMS记录发货、ERP按发货接口自动确认收入、财务使用ERP销售明细选样。该链路同时涉及业务系统、接口、自动控制和IPE。

完成后应能回答

  • 为什么只检查ERP可能不足？
  • 原始业务事实和最终会计记录分别在哪里？
  • 财审使用系统报表时为什么要验证其可靠性？

W1 · LEARNING 06

IT问题如何连接到财审应对

KMT-M1-W1-L06

学习目标

能够说明一个IT控制问题可能如何影响财审对控制或系统数据的依赖，并提出可能的后续程序。

核心内容

  • ITGC问题可能影响系统环境可靠性，例如高权限、变更不受控、日志缺失。
  • ITAC问题可能直接影响业务处理和财务数据，例如自动成本计算错误。
  • Interface问题可能造成数据漏传、重复或跨期。
  • IPE问题可能使财审使用的选样总体、分析数据或控制报表不可靠。
  • 控制问题不等于已发生财务错报，需要分别评价控制风险和实际错报证据。
  • 财审应对可能包括降低控制依赖、扩大实质性测试、重新取得数据或增加期后验证。

判断与执行步骤

  1. 明确IT问题影响什么系统或控制。
  2. 确认它与哪个重大业务流程相关。
  3. 判断可能影响哪些科目和认定。
  4. 判断财审原计划是否依赖该控制或数据。
  5. 确认是否有补偿控制。
  6. 提出适当的财审或IT进一步程序。

常用资料 / 审计证据

  • IT测试结果。
  • 财审审计计划。
  • 控制依赖说明。
  • 相关财务明细。
  • 补偿控制证据。

应用场景

ERP超级管理员可以修改财务配置。需要进一步确认实际权限、操作日志和财审是否依赖相关ITAC，而不能仅凭“存在超管”判断财务报表已错。

完成后应能回答

  • 控制缺陷和财务错报有什么区别？
  • IT问题什么时候会影响财审控制依赖？
  • 如何向财审说明IT测试结果的实际意义？

W2 · LEARNING 01

事实、客户解释与审计判断

KMT-M1-W2-L01

学习目标

能够区分已经通过证据确认的事实、客户解释和审计人员自己的推断。

核心内容

  • 事实应当有可复核证据支持，例如日志显示某账号3月8日登录。
  • 客户解释是一种信息来源，需要通过系统、业务或财务证据进一步核验。
  • 审计判断是基于事实、控制目标、风险和证据形成的专业结论。
  • 客户认可或不认可问题，不决定审计事实是否成立。
  • 客户解释合理时，应取得能够支持解释的资料；解释无法验证时，需要保留证据缺口。
  • 底稿中事实、解释和判断应分别表达，避免混在一起。

判断与执行步骤

  1. 先写已确认事实。
  2. 单独记录客户解释。
  3. 识别解释中需要验证的关键点。
  4. 取得独立证据。
  5. 比较事实与解释是否一致。
  6. 形成自己的初步判断。

常用资料 / 审计证据

  • 系统日志。
  • 业务单据。
  • 客户书面说明。
  • 制度/流程。
  • 财务数据。

应用场景

离职账号晚7天停用，客户解释“期间没有登录，所以没有风险”。需要先确认停用时点和日志，再分别评价控制执行偏差和实际使用风险。

完成后应能回答

  • 客户解释和审计事实有什么区别？
  • 客户不认可问题时，审计判断依据应该是什么？
  • 解释合理但没有证据时应怎样记录？

W2 · LEARNING 02

从问题描述到控制目标

KMT-M1-W2-L02

学习目标

能够把一个表面现象转化为需要评价的控制目标和风险。

核心内容

  • 表面问题例如“密码只有6位”“账号未停用”“没有测试记录”，本身只是事实或现象。
  • 需要继续回答该事实对应的风险是什么，例如未经授权访问、错误变更上线。
  • 控制目标描述企业应达到的状态，例如“离职用户应及时失去系统访问权限”。
  • 控制目标帮助决定应取得哪些证据、异常是否重要。
  • 同一现象在不同业务和系统环境中风险程度可能不同。
  • 没有明确控制目标时，测试容易变成对制度条款的机械核对。

判断与执行步骤

  1. 写明发现的事实。
  2. 分析可能导致什么错误或未经授权行为。
  3. 判断是否影响重大业务或财务数据。
  4. 形成控制目标。
  5. 检查企业现有控制是否覆盖该目标。
  6. 据此设计取证和判断。

常用资料 / 审计证据

  • 控制制度。
  • 系统配置。
  • 风险控制矩阵。
  • 业务/财审重要性资料。
  • 执行记录。

应用场景

数据库备份只保留7天。是否构成重大问题，需要结合恢复目标、数据可重建性、灾备要求和财务报告依赖判断。

完成后应能回答

  • 为什么不能看到一条制度不符合就直接下结论？
  • 控制目标与控制活动有什么区别？
  • 同一个技术事实为什么在不同系统上风险可能不同？

已有证据能支持到哪一步

KMT-M1-W2-L03

学习目标

能够判断每份材料具体证明什么，并避免结论超出证据。

核心内容

  • 截图通常证明某时点的系统状态，不能自动证明全年执行。

  6. 形成当前可支持的判断。

证据不足时的替代证据

KMT-M1-W3-L01

学习目标

能够在原计划证据无法取得时，回到审计目标寻找其他能够支持同一事实的证据。

核心内容

  • 替代证据不是随便换一份资料，而是需要回答同一个审计目标。
  • 原证据缺失时，先明确原本想证明什么。
  • 可从系统日志、独立业务记录、第三方资料、财务记录等寻找替代来源。
  • 替代证据的可靠性、期间和覆盖范围需要单独评价。
  • 多个弱证据相互印证有时可以形成较强证据链。
  • 如果找不到足够替代证据，需要保留范围限制或控制评价影响。

判断与执行步骤

  1. 明确原测试目标。
  2. 说明缺失的原证据。
  3. 列出可替代的数据源。
  4. 评价每个数据源能证明什么。
  5. 组合证据并核验一致性。
  6. 判断是否足以支持结论。

常用资料 / 审计证据

  • 系统日志。
  • 业务单据。
  • 第三方/银行证据。
  • 财务数据。
  • 邮件、审批和工单。

应用场景

客户无法提供用户申请单，但可提供HR入职信息、权限开通日志、部门负责人邮件审批。需要判断组合后能否支持授权和及时开通。

完成后应能回答

  • 替代证据必须满足什么条件？

  • 替代证据仍不足时应该怎样处理？

W3 · LEARNING 02

补偿控制的识别与测试

KMT-M1-W3-L02

学习目标

能够判断某一主要控制不足时，是否存在其他控制降低相同风险，并验证补偿控制实际有效。

核心内容

  • 补偿控制必须能够针对相同或高度相关的风险。
  • 控制存在不等于有效，需要测试设计和执行。
  • 补偿控制可能是事前审批、事后复核、日志监控、独立对账等。
  • 补偿控制的频率和及时性要足以发现问题。
  • 如果风险发生后很久才发现，补偿效果可能有限。
  • 补偿控制不能只依据客户口头说明。

判断与执行步骤

  1. 明确原控制缺口和风险。
  2. 寻找其他能覆盖该风险的控制。
  3. 评价设计是否及时且有效。
  4. 取得执行证据。
  5. 测试异常是否被发现并处理。
  6. 综合评价剩余风险。

常用资料 / 审计证据

  • 复核记录。
  • 监控报表。
  • 日志审阅。
  • 对账记录。
  • 异常处理工单。

应用场景

IT经理拥有超级管理员权限，但所有高风险操作均通过堡垒机录像并由另一名负责人每周复核。需要验证这一复核是否足以构成补偿控制。

完成后应能回答

  • 什么样的控制才能称为补偿控制？
  • 事后复核的频率为什么重要？
  • 客户说“我们会看日志”为什么不够？

W3 · LEARNING 06

备份、恢复测试与证据边界

KMT-M1-W3-L06

学习目标

能够区分“有备份”“备份成功”“备份可恢复”三个不同结论，并在恢复测试缺失时设计替代程序。

核心内容

  • 备份策略需要明确范围、频率、介质、保留周期和责任人。
  • 备份任务成功日志只能证明任务运行，不证明备份数据可用。
  • 恢复测试可以证明备份在需要时能够实际恢复。
  • 没有正式恢复测试时，可了解是否有实际恢复、迁移、灾备切换等替代证据。
  • 恢复能力重要程度与系统关键性、RTO/RPO和数据可重建性有关。
  • 结论应区分设计缺口、执行缺口和实际数据丢失风险。

判断与执行步骤

  1. 确认备份策略。
  2. 验证备份范围和任务执行。
  3. 确认失败处理。
  4. 检查正式恢复测试。
  5. 没有恢复测试时寻找实际恢复证据。
  6. 结合系统重要性评价影响。

常用资料 / 审计证据

  • 备份策略。
  • 任务日志。
  • 失败告警。
  • 恢复测试记录。
  • 实际恢复/迁移工单。

应用场景

数据库每天备份且日志均成功，但两年没有正式恢复演练。去年曾因服务器迁移实际恢复过数据库。需要判断该实际恢复能否作为部分替代证据。

完成后应能回答

  • 备份成功与可恢复有什么区别？
  • 什么证据可以替代正式恢复测试？
  • 系统关键性为什么影响问题定性？

W4 · LEARNING 01

风险、控制目标与控制活动

KMT-M1-W4-L01

学习目标

能够区分风险、控制目标和控制活动，并用它们作为测试程序设计的起点。

核心内容

  • 风险描述可能发生的错误或未经授权行为。
  • 控制目标描述企业希望达到的状态。
  • 控制活动是企业实际采取的措施。
  • 同一风险可以有不同控制活动。
  • 测试程序用于验证控制设计和执行是否达到控制目标。
  • 财务报告相关测试还需要说明可能影响的科目和认定。

判断与执行步骤

  1. 写明业务/IT风险。
  2. 判断是否与重大财务数据相关。
  3. 形成控制目标。
  4. 理解企业控制活动。
  5. 评价设计是否合理。
  6. 再设计测试程序。

常用资料 / 审计证据

  • 制度。
  • 流程图。
  • 控制矩阵。
  • 系统配置。
  • 财审风险清单。

应用场景

风险：离职人员仍可访问系统；控制目标：离职人员应及时失去访问权限；控制活动可能是HR自动触发停用或IT每日处理离职清单。

完成后应能回答

  • 风险、控制目标和控制活动有什么区别？

  • 如何说明该控制与财审的联系？

W4 · LEARNING 02

KMT-M1-W4-L02

学习目标

能够从零设计访问、变更、运维或备份中的常规ITGC程序。

核心内容

W4 · LEARNING 04

测试步骤与预期证据

KMT-M1-W4-L04

学习目标

能够让每一步程序都有明确目的，并知道预期取得什么证据。

核心内容

  • 程序描述应使用可执行动作，例如检查、核对、重算、追踪、复现。
  • 每一步都应对应一个具体风险或控制目标。
  • 预期证据应明确来源和期间。
  • 截图、日志、系统导出、审批、第三方资料的证明力不同。
  • 程序执行过程中如果证据与预期不一致，应及时调整。
  • 底稿应让Reviewer能够从程序追到证据和结论。

判断与执行步骤

  1. 逐步写测试动作。
  2. 在每一步旁写测试目的。
  3. 写预期证据。
  4. 执行并交叉引用证据。
  5. 记录差异。
  6. 根据结果追加程序。
  7. 形成结论。

常用资料 / 审计证据

  • 底稿索引。
  • 证据文件。
  • 截图。
  • 日志。
  • 独立核对资料。

应用场景

测试高权限账号时，程序不能只写“检查管理员”，而应明确取得管理员总体、确认权限范围、检查授权、核对期间操作和补偿复核。

完成后应能回答

  • 怎样判断一条程序是否可执行？

  • Review人员怎样从程序快速判断证据是否够？

W4 · LEARNING 05

ITAC测试设计

KMT-M1-W4-L05

学习目标

能够从风险、系统逻辑、参数、输入、处理、输出和依赖完整设计ITAC测试。

核心内容

  • ITAC常见类型包括自动计算、系统限制、自动审批、自动匹配和自动记账。
  • 测试前必须明确ITAC对应的业务/财务风险。
  • 系统逻辑和关键参数决定控制如何运行。
  • 输入数据或主数据错误会导致ITAC结果错误。
  • 正向、反向、边界或重算测试可验证处理逻辑。
  • ITAC还依赖配置修改权限、程序变更和运行环境等ITGC。

判断与执行步骤

  1. 写风险和财审目的。
  2. 理解系统逻辑。
  3. 识别参数和输入。
  4. 验证输入可靠性。
  5. 设计正向/反向/重算测试。
  6. 核对输出。
  7. 评价ITGC依赖。
  8. 形成结论。

常用资料 / 审计证据

  • 系统配置。
  • 主数据。
  • 测试交易。
  • 异常清单。
  • 相关ITGC资料。

应用场景

付款100万元以上自动要求CFO审批。测试应覆盖阈值配置、100万元边界、不同金额审批路径、审批人映射和流程变更。

完成后应能回答

  • ITAC为什么不能只测试一个历史成功样本？
  • 关键输入和参数有哪些？
  • ITGC问题如何影响ITAC结论？

W4 · LEARNING 06

异常处理、结论与财审影响

KMT-M1-W4-L06

学习目标

能够把测试结果转化为有证据边界的控制结论，并说明对财审依赖的影响。

核心内容

  • 测试异常首先需要确认事实和原因。
  • 区分资料不足、个别例外、系统性执行问题和设计问题。
  • 考虑是否存在补偿控制。
  • 评价异常数量、性质、金额、期间和权限强度。
  • 控制结论和财务错报结论要分开。
  • 如果控制不能依赖，需要说明财审可能增加何种实质性程序或替代控制测试。

判断与执行步骤

  1. 确认异常事实。
  2. 补充证据。
  3. 分析根因和范围。
  4. 测试补偿控制。
  5. 判断控制设计/执行结论。
  6. 评估财审影响。
  7. 写最终底稿结论。

常用资料 / 审计证据

  • 异常样本。
  • 补充日志。
  • 业务/财务数据。
  • 补偿控制。
  • 财审计划。

应用场景

10个变更样本有1个缺测试记录，但变更只修改报表展示格式。需要结合异常性质、财务影响、其他控制和总体情况形成结论。

完成后应能回答

  • 一个样本异常为什么不一定等于全年控制失效？
  • 控制结论和财务错报结论怎样分开？
  • IT控制不能依赖时财审可能怎样应对？
