W1 · CAATs

从审计问题开始

KC-T1-01

目标

能够先定义要回答的审计问题，再决定数据和工具。

核心内容

  • CAATs是以数据处理方式执行审计程序，并直接服务于明确的审计目标。
  • 审计问题要明确对象、期间、风险和预期结论。
  • 离职账号案例可关注及时停用、离职后登录、高权限操作三个层次。
  • 接口案例可关注完整性、准确性、失败重跑和截止。
  • Excel、SQL、Python只是工具，先选最简单可行方式。
  • 编码或Join之前先让别人看得懂任务目的。

执行步骤

  1. 写1-2句话审计问题
  2. 定义期间和对象
  3. 明确预期输出
  4. 列最小数据需求
  5. 确认口径
  6. 再决定工具

需要留下的成果 / 证据

  • 任务说明
  • 数据需求表
  • 业务口径说明

应用场景

任务可以定义为：“验证审计期间离职人员是否及时失去系统访问权限，并识别离职后仍有登录或高风险操作的账号”。

完成后应能回答

  • 这项分析最终要支持什么结论？
  • 如果没有登录日志，结论能支持到哪一步？
  • 为什么审计问题和业务口径需要在取数前确定？

W1 · CAATs

数据需求与业务口径

KC-T1-02

目标

能够明确字段、主键、期间、状态和排除规则。

核心内容

  • 数据需求应围绕审计问题设计。
  • HR、账号和日志需要可靠关联键。
  • 订单与收入可能存在一对多、拆单和跨系统主键问题。
  • 日期字段要区分离职日、停用日、登录日、发货日、记账日。
  • 状态值、币种、正负方向和取消/退款口径需要提前说明。
  • 口径不清会产生大量假异常。

执行步骤

  1. 列事实和字段
  2. 确认主键/关联键
  3. 确认日期口径
  4. 确认状态口径
  5. 确认特殊交易
  6. 形成数据字典

需要留下的成果 / 证据

  • 字段清单
  • 数据字典
  • 业务口径确认

应用场景

离职人员姓名相同、账号命名不统一时，应优先使用工号、邮箱或系统User ID等稳定标识进行关联。

完成后应能回答

  • 为什么主键是数据分析前提？
  • 日期字段差异会怎样影响审计判断？
  • 哪些特殊情况需要单独保留并分类分析？

W1 · CAATs

数据总体与可靠性

KC-T1-03

目标

能够证明分析数据覆盖了应该覆盖的总体。

核心内容

  • 分析结果要进入审计底稿，首先要证明总体可靠。
  • HR离职清单要覆盖审计期间全部离职人员。
  • 账号清单要覆盖目标系统全部相关账号。
  • 日志要确认保留期间和事件范围。
  • 订单/收入总体可以与系统统计、总账或其他独立数据核对。
  • 无法证明全年总体时要缩小结论。

执行步骤

  1. 定义应有总体
  2. 找独立完整性依据
  3. 核对期间/记录数/金额
  4. 调查差异
  5. 记录限制
  6. 确定结论范围

需要留下的成果 / 证据

  • 总体校验表
  • 系统统计
  • 总账/独立数据
  • 限制说明

应用场景

ERP销售明细总额和总账一致，但订单号字段大量为空。金额总体可能可靠，但订单级核对字段仍需进一步验证。

完成后应能回答

  • 什么叫总体完整性？
  • 为什么总额对上不等于所有字段都可靠？
  • 数据期间不完整时结论怎样写？

W1 · CAATs

分析规则与异常分层

KC-T1-04

目标

能够让每条规则有明确审计依据，并区分规则命中与真正问题。

核心内容

  • 规则必须连接风险、控制目标或财报认定。
  • 离职后Active、离职后登录、离职后高风险操作属于不同风险层次。
  • 接口源有目标无、金额差异、失败未落地、跨期可以分开。
  • 规则阈值需要有业务或审计依据。
  • 异常命中后应分高/中/低风险。
  • 误报率过高时要反过来优化规则。

执行步骤

  1. 写规则目的
  2. 写筛选条件
  3. 说明阈值依据
  4. 执行分析
  5. 风险分层
  6. 抽取高风险核验

需要留下的成果 / 证据

  • 规则说明
  • 异常总体
  • 风险分层表

应用场景

500个离职后Active账号中，450个是历史未启用账号、30个无登录、20个有离职后登录。重点应继续集中到20个。

完成后应能回答

  • 规则命中是否等于审计问题？
  • 异常为什么需要分层？
  • 怎样避免低风险记录无限深挖？

W1 · CAATs

异常核验与证据链

KC-T1-05

目标

能够从数据结果继续追系统、业务和财务证据。

核心内容

  • CAATs通常只是识别线索。
  • 权限异常要继续看权限、登录、操作。
  • 接口异常要继续看失败、重跑、目标落地和会计期间。
  • 业务异常可以追审批、业务单据和财务凭证。
  • 客户解释需要证据支持。
  • 最终结论要区分控制偏差和实际财务影响。

执行步骤

  1. 选高风险异常
  2. 写异常事实
  3. 列补充证据
  4. 追实际操作/业务结果
  5. 追财务影响
  6. 形成结论

需要留下的成果 / 证据

  • 核验记录
  • 日志
  • 业务单据
  • 财务记录
  • 异常关闭依据

应用场景

发现离职后3天有登录后，需要继续确认账号权限、实际操作和业务影响。

完成后应能回答

  • 数据结果支持到哪一步？
  • 什么情况下要继续追财务记录？
  • 怎样区分控制问题和实际损失？

把CAATs写进底稿

KC-T1-06

目标

能够把数据程序转成Reviewer无需看代码也能理解的审计底稿。

核心内容

  • 底稿先写审计目标，再写数据。
  • 数据来源、总体完整性和关键口径需要明确。
  • 规则使用业务语言表达，使Reviewer通过底稿即可理解分析逻辑。
  • 结果要体现总体、命中、核验和最终剩余异常。
  • 程序或查询版本需要可追溯。
  • 结论要说明控制/财审影响和限制。

执行步骤

  1. 写审计目标
  2. 写数据来源
  3. 写口径和规则
  4. 记录总体校验
  5. 汇总异常核验
  6. 形成结论

需要留下的成果 / 证据

  • 完整CAATs底稿
  • SQL/Excel文件
  • 运行/处理记录
  • 异常核验清单

应用场景

底稿应说明20条异常如何识别、如何核验、最终剩余多少，以及这些结果影响什么审计结论。

完成后应能回答

  • 一份CAATs底稿最少包含什么？
  • 哪些技术细节不需要放正文？
  • 什么叫可复核、可交接？

重新整理ITGC：访问管理

KC-T2-01

目标

把新增、变更、离职、高权限和定期复核从底稿程序整理成控制目标和判断逻辑。

核心内容

  • 新增关注授权和岗位匹配。
  • 离职关注及时性、登录窗口和实际操作。
  • 高权限关注授权、能做什么、实际使用和责任追踪。
  • 共享账号关注可追责性和补偿控制。
  • 定期复核关注复核人、范围、频率和后续整改。
  • 结论应区分控制偏差与实际风险发生。

执行步骤

  1. 写控制目标
  2. 写常见客户控制方式
  3. 写常见证据
  4. 写异常后程序
  5. 写财审影响
  6. 写Review重点

需要留下的成果 / 证据

  • 个人方法论笔记：SA章节

应用场景

以后看到一个新客户的用户权限流程，应先基于控制目标设计程序，再参考历史底稿校准细节。

完成后应能回答

  • SA最核心的风险是什么？
  • 哪些情况会明显提高问题严重度？
  • 什么证据可以支持及时停用？

重新整理PE：作业、日志、备份

KC-T2-03

目标

把过去可能机械执行的PE程序整理成“对象—风险—证据—结论”。

核心内容

  • 关键批处理影响接口、月结、成本和报表。

KC-T2-05

目标

建立“事实—控制—证据—业务结果—财务影响—结论”的判断框架。

核心内容

  • 规则命中形成待核验异常，后续结合证据完成问题定性。

  • 控制缺陷与实际财务错报需要分别评价，并说明两者之间的影响关系。

  • 需要说明财审是否依赖相关控制或数据。

执行步骤

  1. 写事实
  2. 写控制目标
  3. 整理证据

把Review经验写成规则

KC-T2-06

目标

核心内容

  • Review问题可以分事实、证据、逻辑、方法和表达。
