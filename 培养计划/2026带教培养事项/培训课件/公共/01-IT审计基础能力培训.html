凭证来源

EXERCISE

三个问题，分别从哪里查起

问题一｜产品单价被人改了

未经授权新增或修改产品单价。

直接影响：订单金额、收入和应收可能错误。
先查资料：价格权限、审批、变更日志、订单取价规则和异常订单。
整改办法：限制维护权限，价格变更必须审批并保留前后值。
补偿控制：每日价格异常报表，由业务负责人复核并跟进。
问题二｜平台订单少了

平台订单没有完整传入小A系统。

直接影响：漏发货、漏记收入，或后续人工补单。
先查资料：按平台订单号核对数量和金额，查看失败日志、重传记录和时差。
整改办法：Interface 失败自动报警，并建立失败重试机制。
补偿控制：每日由运营核对平台订单与小A系统接收清单。
问题三｜金蝶出库少了

小A系统销售出库没有完整进入金蝶。

直接影响：收入、成本、库存或凭证记录不完整。
先查资料：按单据编号和物料编码核对数量、金额、状态与 Interface 批次。
整改办法：失败记录进入待处理队列，处理后重新对账。
补偿控制：月末核对小A系统出库汇总、金蝶出库及相关凭证。

AUDIT LOGIC

审计判断链

1风险：平台订单可能没有完整进入小A系统。
2控制目标：所有有效订单均被完整、准确地接收。
3控制：Interface 失败报警、重传和每日对账。
4测试：了解流程，核对总体，抽查报警及处理。
5证据：Interface 日志、失败清单、重传记录、对账表。
6异常：三笔失败记录次日才补传。
7结论与应对：结合影响期间和补偿控制决定是否依赖、是否追加程序。

SCOPE LOGIC

IT审计Scope的判断依据

重大业务流程系统是否直接处理收入、采购、存货、成本、资金、总账等重大流程？
关键自动控制财审是否准备依赖系统自动计算、校验、审批、状态控制等ITAC？
关键系统信息财审是否使用该系统生成的明细、报表、台账或筛选结果作为审计证据？
关键数据传输该系统是否承载重大数据的Interface，或是上下游系统之间不可绕开的节点？
基础设施依赖数据库、操作系统、身份平台等是否直接支撑上述关键系统和控制？
最终判断Scope应与具体财审依赖路径对应，并明确每个纳入对象的审计理由。
项目输出Scope结论至少应写明：纳入对象、纳入理由、对应业务流程/科目/控制，以及重要系统未纳入时的理由。

CONTROL TYPES

控制类型：自动控制、IT依赖人工控制与手工控制

自动控制系统按照既定逻辑自动执行，例如自动计价、系统校验、状态锁定、自动审批。重点：程序逻辑、参数、变更与ITGC。
IT依赖人工控制人员进行判断或复核，但使用系统生成报表、异常清单或系统状态作为依据。重点：人工复核 + IPE可靠性。
手工控制控制执行和证据主要不依赖系统自动处理，例如纸质盘点签字或人工合同复核。重点：通常由财审直接评价执行。
A公司例子：系统自动锁定已发货订单属于自动控制；运营每天复核系统生成的订单差异报表属于IT依赖人工控制。两者测试思路不同，不能都按“截图看一下”处理。

CONTROL TESTING

控制测试的三个层次：设计、实施与运行有效性

01｜设计是否合理这个控制如果按设计执行，是否能够预防或及时发现相关风险？控制频率、执行人、阈值和异常处理是否匹配风险？
02｜是否已经实施控制是否已经配置或实施？通过 walkthrough、配置截图、系统演示、制度和访谈确认控制已经落实到系统配置或实际流程。

CASE

超级管理员账号｜分支判断

背景：财务系统存在 3 个超级管理员账号，其中 1 个由 IT 部门负责人使用。先确认：业务必要性、实名归属、审批、职责分离、日志范围、独立复核和实际操作。

什么都没有没有授权、没有使用限制、没有日志，也没有独立监控。判断：控制不能支持依赖。确定受影响系统和期间，检查高风险操作，并与财审讨论追加程序。
只满足一部分例如账号经批准且实名，但日志不完整或由本人复核。判断：证据仍不足。补查堡垒机/数据库/应用日志，扩大高风险操作检查，并评价其他补偿控制。
关键条件均满足确有必要、审批充分、个人账号、使用受限、日志完整并由独立人员及时复核，未见异常操作。判断：仍记录为高风险权限，但相关控制可以测试；结合样本结果决定是否依赖。
若日志缺失，不能停在“资料未提供”。还要继续问：有没有堡垒机记录、工单、数据库审计日志、变更记录或业务复核可以交叉印证？

📖 Audit Log /ˈɔːdɪt lɔːɡ/审计日志｜谁动过哪份档案的记录本
🔤 Collation / COLLATE排序与比较规则｜决定文本如何排序、匹配，以及是否区分大小写、重音等差异
审计应用：前台页面可能限制修改，但数据库高权限仍可能直接改表；审计需要知道数据从哪张表来、用什么主键关联、谁能写入。做对账、去重或关联时，还要留意不同系统的 Collation 是否一致。
Collation 为什么会影响分析：例如 User01 与 user01 在某些规则下会被视为相同，在另一些规则下则不同。跨系统核对时，如果比较规则不一致，可能产生“假差异”或漏掉重复记录。
概念区分Collation 是文本排序和比较规则；COLLATE 是查询中显式指定比较规则的常见写法。IT审计不需要记数据库语法细节，但要知道它可能影响匹配、去重、JOIN 和 CAATs 结果。

Git 与代码仓库｜Repo、Branch、Commit、Merge Request 是什么

Repository 仓库→Branch 分支→Commit 提交→Merge Request 合并申请→Tag / Release 版本
Repository
一个项目的代码仓库。审计先确认哪些仓库对应财务相关系统、接口或关键脚本。
Branch
不同开发线。常见 main/master、develop、feature。重点看生产分支是否受保护。
Commit
一次代码变更记录，通常包含作者、时间和说明。它证明“代码被改过”，不等于“已上线”。
Merge Request
把代码合并到目标分支的申请。可以配置必须经他人复核后才能合并，是常见补偿性职责分离控制。
常见误区：GitLab里看到某人提交代码，只能证明他改了代码；要证明代码进入生产，还要继续追 Jenkins / CI/CD 发布记录、版本号和上线审批。

CI / CD

Jenkins 与 CI/CD｜代码如何从仓库走到生产

开发提交代码→触发 Pipeline→Build 构建→Test 测试→Approval 审批→Deploy 部署→验证
01Job / Pipeline定义“拉代码—编译—测试—发布”的自动化步骤。修改Pipeline本身也属于高风险变更。
02Agent / Node真正执行构建或部署任务的机器。要知道它能访问哪些生产服务器和网络区域。
03CredentialsJenkins保存的SSH Key、Token、数据库密码或云密钥。拥有凭据管理权限通常属于高权限。
04Build / DeployBuild是把代码变成可运行包；Deploy是把版本发布到目标环境。两者不要混为一谈。
05User / Permission谁能查看、构建、配置Job、修改Credentials、执行生产发布，应按职责分配且一人一号。
共享账号为什么有问题：如果同组多人共用一个Jenkins人工登录账号，系统只能记录“这个账号发布了版本”，无法追溯到具体执行人员。服务账号可以存在，但不应当作为多人日常登录账号。

NETWORK BASICS

网络六个高频概念｜IP、Domain、DNS、Port、Firewall、VPN

IP Address设备或服务在网络中的地址。日志中的源IP可以帮助判断操作从哪里发起，但IP不一定等于某个人。
Domain / URL用户看到的系统地址，例如erp.company.com。域名最终需要解析到服务器或负载均衡地址。
DNS把域名解析成IP地址。DNS异常可能导致系统“地址没变，但访问不了”。
Port同一台服务器上不同服务的逻辑入口。审计不需要背端口，但要理解开放端口意味着一种可访问路径。
Firewall / Security Group控制哪些来源可以访问哪些目标和端口。云平台中安全组承担类似网络访问控制作用。
VPN / Remote Access让外部人员进入内部网络。重点看谁能远程进入生产环境、是否MFA、是否记录登录日志。
不要把网络审计做成渗透测试：IT审计主要确认关键系统的访问边界和管理通道是否合理、是否支持权限控制与操作追溯。

MIDDLEWARE

接口与中间件｜API、Gateway、MQ、Kafka、ESB、ETL

API系统按约定实时请求数据或功能。要关注认证、请求参数、返回结果、失败重试和日志。
API Gateway统一承接API入口、认证、限流和路由。它可能是重要的接口日志和访问控制证据来源。
Message Queue消息队列让系统“先把消息放进去，再由另一端处理”。RabbitMQ、Kafka常见于订单、库存和日志传输。
ESB企业服务总线，负责多个系统之间的集成、转换和路由。财务接口链路中可能是关键中间层。
ETL / BatchExtract-Transform-Load：批量抽取、转换、加载数据。常用于数据仓库、日报、财务数据集成。
审计关注点完整性、准确性、及时性、重复处理、失败重试、异常队列、字段映射及接口对账。
判断方法接口并不一定是一条“线”。中间可能经过网关、消息队列、ESB、临时表或批处理任务，审计要把真实链路画完整。

DATA EXCHANGE

数据文件与格式｜CSV、JSON、XML、SFTP、Encoding、Checksum

01CSV / Excel结构化表格文件。关注字段定义、分隔符、日期和数字格式，以及是否因Excel处理造成精度或前导零丢失。
02JSON / XML常见接口数据格式。JSON常用于API；XML在传统系统集成和报文中也很常见。
03SFTP / File Transfer系统通过文件交换数据，例如每日订单、库存或银行流水。重点看文件是否齐全、是否重复、失败如何处理。

OBSERVABILITY

监控、日志与告警｜Metrics、Logs、Traces 各回答什么

Metrics｜指标CPU、内存、磁盘、响应时间、错误率、队列积压等连续指标。常见：Zabbix、Prometheus、Grafana
Logs｜日志记录具体事件，例如登录、报错、接口失败、数据修改和管理员操作。常见：ELK / Elastic、Splunk、Graylog
Traces｜链路追踪跟踪一次请求经过哪些服务、在哪一步变慢或失败，适合复杂微服务架构。常见：APM、OpenTelemetry等
系统异常→监控发现→Alert 告警→工单 / 处理→恢复→复盘
审计重点不是问“有没有Grafana”，而是确认关键异常能否被及时发现、通知到责任人、形成处理记录并跟踪关闭。

安全工具不等于IT审计范围，但这些名称经常会遇到

EDR / Antivirus终端检测与响应、杀毒软件。关注关键服务器/终端覆盖、策略状态和高风险告警处理。

CLOUD BASICS

云平台基础｜IaaS、PaaS、SaaS 与“谁负责什么”

IaaS云厂商提供计算、存储、网络等基础资源，公司自己管理操作系统、数据库、应用、账号和数据。例：云主机、云硬盘、VPC
PaaS云厂商进一步管理数据库、中间件或运行平台，公司主要负责应用配置、账号权限和数据。例：云数据库、托管Kubernetes
SaaS供应商直接提供可使用的软件，公司更多负责用户、角色、配置、接口和业务数据。例：部分HR、CRM、协同办公系统
Shared Responsibility“上云”不等于控制责任转移。云厂商负责底层设施，不代表客户不需要管理管理员账号、MFA、配置、备份、日志和数据访问。
审计提问：谁拥有云平台Owner/Administrator？是否强制MFA？Access Key如何保管？安全组谁能改？数据库备份由云平台自动完成后，公司是否做过恢复验证？

DEFICIENCY ASSESSMENT

ITGC异常如何定性：按事实、范围和影响逐步判断

1明确控制目标
2确认事实与证据边界
3评价频率、范围及补偿控制
4评估对ITAC、IPE及财审依赖的影响
例1｜离职账号延迟停用需结合总体判断

事实：1名员工离职后3天才停用账号，现有登录日志未见其离职后登录。

继续确认：日志是否覆盖完整期间、账号权限大小、延迟是否为孤例、是否有HR/IDM自动停用或每日复核等补偿控制。

判断思路：“未登录”只能说明暂未发现实际使用，不能消除停用不及时这一控制例外。若为孤例、低权限且日志完整，可结合总体样本评价是否影响控制依赖；若同类情况反复出现，则更可能反映运行有效性问题。

例2｜紧急变更缺少事前审批看紧急流程是否受控

事实：订单接口出现生产故障，开发人员当晚修复并上线；无常规事前审批，但有故障工单、测试记录、部署日志和次日业务复核。

继续确认：制度是否允许紧急变更、谁批准进入紧急流程、生产权限是否临时授予、事后审批和独立复核是否及时。

判断思路：不能仅因缺少常规审批即认定整个变更管理失效。应按紧急变更控制要求评价证据是否完整；若紧急流程本身无授权、无复核且经常被使用，则风险明显上升。

例3｜共享超级管理员且缺少独立日志高风险

事实：多人共用同一超级管理员账号，可修改关键参数和业务数据；无法区分实际操作人，应用层管理员日志也可被该账号删除。

继续确认：是否存在堡垒机、数据库审计日志、工单或其他独立证据；期间是否发生关键参数修改、数据直接更新或权限调整。

判断思路：实名追踪和独立监控均不足时，通常难以支持对相关高权限控制的依赖，还需识别受影响的ITAC、IPE及财审程序，并考虑扩大高风险操作检查。

例4｜备份每天成功，但全年未做恢复测试备份成功≠可恢复

事实：系统每天有备份成功记录，但本年度没有实际恢复测试，也没有证据验证备份文件可用。

继续确认：备份范围是否覆盖数据库、附件和配置；历史是否做过恢复；是否发生过数据丢失或灾难恢复事件；RPO/RTO要求是什么。

判断思路：现有证据可以支持“备份任务执行”，但不足以支持“能够按要求恢复”。应单独评价恢复控制缺口，并结合系统关键性、历史事件和其他容灾措施判断对财务审计依赖的影响。

FULL POPULATION VS SAMPLE

全量分析、抽样和阈值：根据风险选择方法

适合全量分析规则清晰、字段结构化、总体可取得，例如重复订单、离职后登录、接口差异、异常分录特征。

阈值怎么定

全量分析后的判断
